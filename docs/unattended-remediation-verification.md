# 无人值守自动处置：修复与验收

2026-09-26。适用当前工作区；执行格式仍为 v3，数据库升级到 001–015。目标是已配置、已授权场景无需逐次人工批准；外部结果未知、证据不足、动作前提变化时停止写入并可靠通知人工。

## 本次修复

- 发布回退保留完整镜像引用，正常完成和外部成功后的对账都通过同一个事务提交回执、变更记录和验证任务。只允许回退到相邻且已验证的上一发布，部署锁内再次校验发布 ID、迁移声明和镜像引用。
- 重启通过容器 ID 执行，写入前比较容器身份、启动时间和进程状态，禁止覆盖准备之后的人为停止或已经发生的恢复。
- 上游隔离冻结分组、平台、状态和容量下限，执行前重新读取；补偿继承原前置状态，分组或平台被修改时不覆盖。
- 规则、服务配置、验证标准共同决定授权版本。领取、启动恢复和验证都核对当前绑定；换目标或换凭据不会把旧操作对账到新服务。
- 业务指标要求唯一、完整、非负、有限且采样新鲜。使用 `timestamp(selector)` 过滤真实采样时间，以同一个 Prometheus evaluation time 读取，避免把查询时间误当采样时间。空结果、采集失败、旧样本都不能授权自动写入或验证成功。
- 连续验证跨长采样缺口会重新计数；观察期缺失观测会进入 inconclusive，不能写成功记忆或宣称稳定恢复。Worker 和事务提交都执行检查。
- 业务探针还要求完整、合法且包含模型输出的响应；HTTP 200 的错误页、错误对象或空响应不会被当作业务恢复。响应正文不进入日志和结果。
- 失败结果与 `notification_task` 在同一事务中提交；独立 Worker 持续退避重试投递。执行失败、验证失败/未知/复发、待人工处置的诊断和诊断通知失败均有持久路径。投递是至少一次；响应丢失可能产生带同一事件 ID 的重复通知。Webhook 必须返回有效且明确的成功码。
- 单活动执行锁在全部 Worker 启动前取得，Worker 结束后才释放；固定连接失效会停止进程，外部写入前也检查持有权。超时后当前状态未变化不能证明操作不会稍后生效，因此记 unknown 并触发持久全局急停；核查后由管理员恢复。仍不支持多活动副本，也不宣称跨 MySQL/外部系统 exactly-once。
- Webhook 限制 1 MiB、100 条告警、8 个并发、10 秒请求预算；pending 队列最多 1,000 个事件。容量在写事务内检查，过载返回 503，202 仍代表持久化已提交。字段长度和数据库时间范围的永久错误进入 failed，不再阻塞后续告警。
- MySQL 连接池上限 24、空闲上限 8，未显式配置时连接与 IO 超时为 5 秒。队列年龄和深度在后台按有限查询预算刷新；监控覆盖摄入、诊断、验证和通知延迟以及状态库不可读。

## 自动模式的启动门槛

任一规则使用 `mode: auto` 时，启动要求：

1. 诊断模型配置有效，具有可识别的管理员身份，可执行急停与恢复。
2. 配置实际通知渠道。没有渠道时不能悄悄用 Noop 进入自动运行。
3. 至少连续 3 次验证通过，并配置足以观察复发的 watch 窗口。
4. 自动重启配置业务探针；`/health` 单独成功不证明业务恢复。
5. 自动回退和隔离配置正数 `min_requests`，验证窗口长于 5 分钟流量窗口。
6. 动作本身可用，执行前业务指标完整、当前授权有效、未急停、无服务冲突、预算未耗尽。

具体阈值仍按真实业务校准。启动配置检查只证明门槛存在，不能替代通知送达、模型质量、探针费用和生产部署锁的实际验证。

## 已执行的验收

- Go 全量测试与 race 检查，包括独立 MySQL Store / API / Diagnose 库的事务、故障注入和恢复测试。
- 空库与旧版状态库的迁移模式，完整执行 001–015；维护命令在新通知表创建之前仍能离线退役旧审批。
- 真实 Docker 与 MySQL：异常报文隔离 → 自动审批 → 实际重启 → 真实 HTTP 健康/业务探针 → 连续通过 → 观察稳定 → 不重复执行 → resolved 关单。容器为独立 Python HTTP 测试服务；模型和指标是确定性输入。这证明执行闭环，不等同于真实 sub2api/模型生产效果。
- 真实 Prometheus v2.54.1：3 分钟前的样本仍能被原始 instant query 返回，但新鲜度过滤会拒绝它；更新采样后恢复可用。
- 真 MySQL、多动作执行链：正常回退、外部成功但命令返回错误后的回退对账、隔离前容量减少、验证失败/未知后补偿、分组/平台变化阻止补偿，共 7 个场景。Docker API/发布脚本及 sub2api 管理接口为受控 fixture，真实 Action、Policy、Executor、Store 和 Verifier 参与。
- 独立复审补充回归覆盖配置变更后的中断恢复、验证绑定、租约丢失、缺失监控、Webhook 假成功、准备之后人为停止。

## 部署与启用

已有 001–014 状态库必须先停进程、备份、执行 [015_notification_task.sql](../migrations/015_notification_task.sql)，再运行 `cmd/retire-approvals -check`。完整路径见 [升级说明](execution-trust-upgrade.md)。在途旧审批因配置/动作版本不匹配会转为未知并触发急停，应先完成在途任务或核查后恢复。

按 [config.example.yaml](../config.example.yaml) 配置可信服务目录、允许动作、模型、管理员、通知、业务探针与验证预算；仅将验收通过的目标规则改为 auto。确认通知到达实际接收人，真实业务探针使用专用低成本身份，发布命令与人工/CI 共用部署锁，外部心跳能发现宿主机整体失联。

本次没有迁移生产数据库、修改生产权限或启用生产 auto。本机 `config.yaml` 仍使用旧配置，缺少新的服务/规则、管理员、通知和业务探针；不能直接拿它运行新版本。真实 sub2api 的坏版本、上游隔离及补偿演练，以及真实模型冻结回放和持续流量测试，仍需在目标部署的隔离环境完成后才有生产放行证据。
