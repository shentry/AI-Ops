# AWS 部署与 k6 压测报告（2026-09-17）

## 结论

**本次没有把 MySQL 压崩，但明确测到了“HTTP 接收跟得上、后台消费跟不上”。不能把 250 Webhook/s 的接收结果当作持续处理容量。**

- 重复、单条告警 **250 Webhook/s × 20 秒**：5,001 次全部返回 202，HTTP P95 **14.75 ms**；pending 采样峰值 **3,454 个 Webhook**，发现停压后约 **35.32 秒**才观察到排空。
- 新指纹、单条告警 **100 Webhook/s × 20 秒**：HTTP P95 **11.64 ms**；pending 峰值 **843**，观察排空耗时 **14.63 秒**。
- 单条告警 **50 Webhook/s × 60 秒**，以及新指纹批量告警 **10 Webhook/s × 10 条/包 × 60 秒**，本次窗口内没有持续积压。它们是经过验证的短时工作点，**不是生产限流值或长期容量承诺**。
- 15 个完整阶段接受 **23,815 个 Webhook / 38,242 条 payload 告警**。加上冒烟和一次提前停止阶段，共 **24,244 个 Webhook 全部对账到 processed**，最终 pending/failed 均为 0。
- 测试容器未 OOM、未新增重启。Sub2API 的全部 288 次健康采样均为 200，容器身份、启动时间、重启次数与原会话清理后的基线一致。**这不等于验证了 Sub2API 真实业务请求完全不受影响。**

当前最直接的问题是消费能力与入口流量之间缺少容量约束，而不是“缺少 MQ 就一定立即崩库”。

## 2. 测试覆盖什么

```text
k6 → Webhook → INSERT raw_event → 202
                        ↓
                  单个 ingest worker
                        ↓
           去重 + incident 归并 + skip run + processed
```

- Alertmanager v4 合成报文；`severity=info → skip`，`group_by=[labels.service]`，`min_alerts=1`。
- duplicate：同一阶段的 labels、annotations、startsAt 固定；重复报文仍写 raw_event，后续 alert 全量去重并更新心跳。
- unique：每个 Webhook 的 service/instance 身份不同；每包产生一个 incident/run，每条告警产生一个新指纹。
- batch=10 时，同包 10 条告警共享 service，因此是**一包一个 incident**，不是 10 个。
- 每秒另读一次 `/api/v1/control-room/incidents?limit=20`。原脚本的 `/api/v1/incidents?limit=20` 实际不分页，已在正式阶段前改为真实分页接口，避免混入持续增长的全表读取负载。
- 每阶段使用新 RUN_ID，串行运行，开始前要求队列已空。保留历史测试数据，数据库随阶段推进逐渐增长。
- 禁用真实 LLM、外部通知和修复；无 Docker socket 或 Sub2API 数据挂载。run 为 `skip/succeeded` 不表示执行过一次真实诊断。

**不覆盖**公网/TLS、真实 Alertmanager 重试、真实诊断/审批/修复、多实例摄入、数据库故障或小时级稳定性。负载发生器与被测服务共享主机，CPU/内存限额不隔离磁盘 I/O。

统计注意：

- 开放模型首尾调度会使实际数量出现 `rate × seconds + 1`；以上使用 k6 实际计数，不把计划数当实发数。
- 监控目标间隔 2 秒，实际另含 SQL/健康查询耗时；峰值是采样值，可能漏掉更短的尖峰。
- 排空计时从 runner **发现 k6 已退出**后开始，不是从最后一个 HTTP 请求开始。原始记录约 0.06 秒通常只是首次查询耗时，不能写成“精确 60ms 排空”。
- 当前 `processed_at` 在 apply 事务开始前赋值，未包含随后事务执行/提交时间，本报告没有将其作为端到端完成延迟。
- 读取仅 1 req/s，每阶段约 21/61 个样本，不代表高并发控制台容量。各阶段 P95 不能平均成总体 P95。

## 4. 消费瓶颈与资源观察

在相邻两个采样都已有积压的发压区间，以 **已提交 processed 数差 / 采样间隔**计算消费速率，中位数约为：

| 阶段 | 输入 Webhook/s | 消费 Webhook/s（上述采样区间中位数） |
|---|---:|---:|
| 重复、1条/包 | 100 | 91.14 |
| 重复、1条/包 | 200 | 76.56 |
| 重复、1条/包 | 250 | 71.58 |
| 新指纹、1条/包 | 100 | 55.83 |
| 新指纹、10条/包 | 25 | 16.12 |

这些是特定负载下的观测值，不是一个固定的“系统 TPS”。例如重复告警 250/s 阶段，入口接近 250/s，消费约 72/s，队列自然增长；停压后该阶段有积压的排空采样中位数约 104/s。

| 资源 | 观察 |
|---|---|
| MySQL CPU | 采样区间峰值约 77.82% 单核，接近 0.80 核限额；批量场景有 CPU throttling |
| server CPU | 峰值约 22.22% 单核，低于 0.60 核限额 |
| k6 CPU | 峰值约 12.05% 单核，低于 0.25 核限额；无 dropped iterations |
| MySQL 连接 | 采样 Threads_connected 3–7；全局 Max_used_connections 最高 8/100，含监控查询 |
| MySQL 等待/错误计数 | 已记录的 Aborted_connects、Slow_queries、行锁等待、buffer-pool wait-free 均为 0 |
| 后半程工作集峰值 | MySQL 472.95 MiB；server 13.41 MiB；k6 16.55 MiB。早期记录未采工作集，不混同为全程值 |
| 主机可用内存 | 采样最低约 2.21 GiB |
| Sub2API 健康 | 288/288 次 200，耗时约 0.91–10.18 ms；最终检查 200 |

最终 MySQL `memory.events.max=411`、`oom=0`、`oom_kill=0`：曾触及 cgroup 内存硬限额并发生回收，**不能说全程没有内存压力**。MySQL 总 cgroup 内存采样峰值约 766.65/768 MiB，包含文件缓存。

代码与观察对应：

- `internal/api/alertmanager.go:59–69`：raw_event 落库后即 202，不等待消费。
- `internal/store/rawevent.go:73–80`：每个合法 JSON 请求先插入完整原文。
- `internal/ingest/worker.go:94–131`：唯一消费 goroutine，串行 drain。
- `internal/store/rawevent.go:113–146`：同包逐条去重/关联与 processed 状态在一个事务中提交。
- `internal/ingest/worker.go:206–218`：全量重复仍更新 Incident 心跳。
- `internal/store/db.go:22–31`：当前业务代码没有显式设置连接池预算。
- `internal/store/incident.go:262–290`：旧列表无 LIMIT；控制台列表在 SQL 侧限制条数。

因此已证实的限制是**单消费者事务链路的处理速度低于高输入速度**。本轮未做磁盘/SQL 逐操作 profiling，不能进一步断言每个阶段都由某一条 SQL、fsync 或同一种硬件瓶颈独占主导。

## 7. 下一步建议

**先补有界入口、数据库预算与积压治理，再决定是否引入 MQ。**

1. 入口按并发、报文大小/告警条数、队列长度或年龄做准入；过载在接收成功前返回可重试错误，不能先 202 再丢。
2. 显式限制连接池和请求/事务等待时间，给控制台、审批等共享访问留预算。
3. 监控已提交消费速率、最老 pending、失败/重试、原文保留空间；分批清理或归档已处理 raw_event。
4. 如果业务必须在数据库不可用或明显超出消费能力的洪峰期间仍持续接收，再把独立持久 MQ 放在 MySQL **之前**；不要保留“先入 MySQL 再入 MQ”的双队列路径。

生产阈值应在真实报文、诊断负载、数据规模、磁盘和持续时间下重新验证。本轮 50 Webhook/s 的单条场景结果不能直接套用于 10 条/包，更不能直接代表 LLM 诊断能力。
