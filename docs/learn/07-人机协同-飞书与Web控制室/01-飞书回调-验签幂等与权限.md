# 飞书回调：验签、幂等与权限

> 所属：[亮点七 · 人机协同——飞书与 Web 控制室](README.md)

## 一句话

飞书把卡片按钮点击和群消息推到 `/integrations/feishu/events`。**验签和解密交给官方 SDK**；业务层负责：按事件 ID 记录回执，同一事件只处理一次；操作人必须在白名单里；按钮里的 plan_hash 必须和审批单一致；群消息只接受配置的群、非机器人发送、并且能关联到某个 incident 的消息。

## 先弄懂：飞书回调的机制

- **卡片回调**：用户点击卡片按钮，飞书把按钮里预设的 `value`（本项目是 `{action, approval_id, plan_hash}`）连同操作人信息 POST 到回调地址。
- **消息事件**：群里有人发消息（比如在卡片线程里 @ 机器人），飞书推送 `im.message.receive_v1` 事件。
- **验证与加密**：飞书用 Verification Token 标识来源，用 Encrypt Key 加密事件体。首次配置回调地址时，还有一次 challenge 握手。
- **重试**：接收方没有及时正确响应，飞书会重新推送同一个事件（事件 ID 不变）。

## 分层：SDK 做什么，业务做什么

```go
// 摘自 internal/notify/feishu/callback.go（有删减）
// CallbackHandlers 是业务回调。它们在 SDK 完成身份验证和解码之后执行；
// 本包不重复实现签名或 AES 处理
type CallbackHandlers struct {
	CardAction     func(context.Context, *callback.CardActionTriggerEvent) (*callback.CardActionTriggerResponse, error)
	MessageReceive func(context.Context, *larkim.P2MessageReceiveV1) error
}

// 创建官方 EventDispatcher，注册两个回调：卡片按钮、机器人收消息
func NewDispatcher(verificationToken, encryptKey string, handlers CallbackHandlers) *larkdispatcher.EventDispatcher {
	dispatcher := larkdispatcher.NewEventDispatcher(verificationToken, encryptKey)
	return RegisterHandlers(dispatcher, handlers)
}

// 两种事件类型都会注册：业务回调缺失时返回受控的错误，而不是悄悄返回成功
func RegisterHandlers(dispatcher *larkdispatcher.EventDispatcher, handlers CallbackHandlers) *larkdispatcher.EventDispatcher {
	// ……缺失的 handler 替换成返回错误的占位……
	return dispatcher.OnP2CardActionTrigger(cardHandler).OnP2MessageReceiveV1(messageHandler)
}
```

| 层 | 负责 | 为什么这样分 |
|---|---|---|
| 官方 SDK | challenge 握手、Verification Token 校验、AES 解密、事件解析 | 密码学和协议细节不自己写，跟随官方更新 |
| 业务层 | 幂等、授权、版本校验、业务决策 | 这些和本项目的数据模型强相关 |

## 业务层第一关：事件回执，保证幂等

```go
// 摘自 internal/notify/feishu/callback_business.go（有删减）
func (b *CallbackBusiness) claimReceipt(ctx context.Context, eventID, eventType string) (bool, error) {
	receipt := store.IntegrationEventReceipt{EventID: eventID, Provider: b.provider, EventType: eventType,
		ProcessedAt: time.Now().UTC(), Result: "processing"}
	return b.store.ClaimIntegrationEventReceipt(ctx, receipt) // 事件 ID 唯一：插入成功才算认领到
}
```

每个回调一进来，先用事件 ID 插入一条回执：

- 插入成功 → 第一次见到，继续处理；处理完把结果（approved / denied / forbidden / invalid / conflict……）写回回执。
- 插入失败（已存在）→ 重复推送，直接返回「该操作已处理」。
- 处理中遇到**系统错误**（不是业务拒绝）→ 删除回执，让飞书的重试能重新处理。

## 第二关：操作人白名单

```go
func (b *CallbackBusiness) allowed(openID string) bool {
	if strings.TrimSpace(openID) == "" || len(b.allowlist) == 0 {
		return false // 白名单为空：谁都不能审批（默认拒绝）
	}
	_, ok := b.allowlist[openID]
	return ok
}
```

飞书群里的任何人都能看到卡片，但只有配置在 `operator_allowlist` 里的人（按飞书 open_id）才能审批。决策人记为 `feishu:<open_id>`。

## 第三关：卡片版本（plan_hash）

按钮的 `value` 里带着生成卡片时的 plan_hash。回调时和审批单当前的 hash 比较，不一致就提示「审批计划已变更，请刷新卡片」。然后在数据库事务里，带着这个 hash 再做最终决策（详见[亮点三第 5 篇](../03-确定性闸门与规则授权/05-人工审批-飞书卡片与有效期.md)）。

决策完成后，异步更新原卡片，显示「已批准 / 已拒绝」，其他人看到的就是最新状态。

## 群消息：怎么把一句话关联到 incident

值班人员可以在诊断卡片的线程里直接提问，比如「为什么判断是进程退出而不是 OOM？」。问题是：**这句话问的是哪个 incident？**

**绑定表**解决这个问题：

```go
// 摘自 internal/notify/feishu/binding.go 的注释
// BindingNotifier 包装飞书发送器，发送成功后记录 message_id 与 incident 的绑定。
// 绑定写入失败不会撤回已经发出的飞书消息
```

- 每条发出去的卡片，都记录「飞书消息 ID ↔ incident」；
- 有人在卡片线程里回复时，根据被回复消息的 ID 找到 incident；
- 也可以在消息里显式写明 incident 编号；两者都有但不一致时，忽略这条消息。

收消息的完整过滤：

```text
① 事件回执幂等
② 只接受配置的那个群（chat_id）
③ 忽略机器人自己发的消息
④ 必须能关联到一个 incident（线程绑定，或显式编号）
⑤ 为这条提问也创建绑定：回答要回复到这条消息所在的线程，不能串到别的线程
⑥ 调用 conversation.Service.Ask 入队，立即返回（不在回调里调用模型）
```

回答生成后，追问 worker 会根据第 ⑤ 步的绑定，把回答回复到原消息的线程里（见第 3 篇）。

## 为什么回调里绝不调模型

飞书要求回调在几秒内响应，超时就会重试。如果在回调里调模型（几十秒），就会：回调超时 → 飞书重试 → 同一个问题被处理多次。所以回调只做「校验 + 入队」，真正的工作交给后台 worker。这和告警 Webhook「先落库再处理」是同一个思路。

## 常见追问

- **卡片上的「请求补充证据」为什么在飞书里点不了？** 代码里明确返回「请在 Web 控制室请求补充证据」。补充证据需要填写具体要查什么，适合在 Web 上操作。
- **飞书的 open_id 能伪造吗？** 操作人信息来自经过 SDK 验证和解密的事件体，不来自请求头或按钮值，外部无法伪造。
- **为什么还保留普通 webhook 通知？** 没有配置飞书企业应用时，可以用普通 webhook 只发通知（没有按钮和回调）。企业应用模式下不会回退到普通 webhook，选择是显式的。
