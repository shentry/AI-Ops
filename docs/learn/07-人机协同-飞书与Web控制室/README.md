# 亮点七：人机协同——飞书与 Web 控制室

> 返回：[知识库首页](../README.md)

## 一句话（简历写法）

构建飞书与 Web 双端的人机协同入口：飞书回调由官方 SDK 验签解密，业务层按事件 ID 幂等处理、按操作人白名单授权、按 plan_hash 校验卡片版本；Web 控制室基于服务端身份（个人 Token 与签名会话）和三级角色控制权限，用数据库分页轮询的 SSE 推送事件流；对话追问是第二个只读 Agent，异步排队、带引用作答，不产生任何动作。

## 它解决什么问题

- **人在哪里介入**：值班人员主要在飞书里，看详情、做复杂操作要去 Web。
- **回调可能被伪造、重复、过期**：飞书会重试推送，旧卡片可能还挂在群里。
- **谁能做什么**：看、批准、急停，需要不同的权限。
- **人想问「为什么」**：需要一个能查数据、但不能动手的问答入口。

## 方案全景

```text
            飞书群                                    浏览器（Web 控制室）
  ┌─────────────────────────┐                ┌──────────────────────────────┐
  │ 诊断卡片：根因 / 建议 /   │                │ 登录（个人 Token → 签名会话）   │
  │ 批准 / 拒绝 / 打开控制室   │                │ incident 列表 → 作战室：        │
  │ 在卡片线程里追问 @机器人   │                │  流程图 / 事件时间线（SSE）/    │
  └───────────┬─────────────┘                │  步骤检查 / 问题面板 / 审批 /     │
              │ 回调                           │  追问 / 重诊 / 补充证据           │
              ▼                                │ 自动处置页：规则、急停、效果报表    │
  /integrations/feishu/events                  └──────────────┬───────────────┘
  官方 SDK：验证 token、解密                                     │ /api/v1/...
  业务层：事件回执幂等 → 白名单 → plan_hash → 决策 / 入队追问      │ Auth：身份 + 角色 + CSRF
              │                                               │
              └───────────────────┬───────────────────────────┘
                                  ▼
          同一套服务：approval.Service.Decide、conversation.Service.Ask、
          RequestRun（重诊）……所有耗时工作都排队，HTTP 请求里不跑模型
```

## 读完本亮点你会知道

- 飞书回调的安全分层：哪些交给 SDK，哪些由业务层负责。
- 卡片消息和 incident 怎么关联，线程里的追问怎么找到对应的 incident。
- Web 的身份与权限模型，为什么 SSE 不用内存 channel。
- 对话追问 Agent 和诊断 Agent 有什么不同，为什么它必须只读。

## 面试怎么讲

**30 秒版本：**
人主要在两个地方介入：飞书和 Web 控制室。飞书回调的验签和解密交给官方 SDK，业务层做三件事：按事件 ID 记录回执，保证重复推送只处理一次；按操作人白名单授权；按按钮里带的 plan_hash 校验卡片是不是最新版本。Web 端身份完全由服务端判定：个人 Token 登录后换成签名会话 Cookie，有 viewer、operator、admin 三级角色，改状态的请求还要带 CSRF 头。实时事件流用 SSE，数据源是数据库，按事件 ID 增量读取，断线重连靠 Last-Event-ID 续传。追问是第二个 Agent，只能用只读工具，回答必须引用真实的事件或步骤 ID，给出的建议不能直接执行。

**常见追问：**

- **为什么 SSE 不用 WebSocket？** 控制室只需要服务端到浏览器的单向推送，SSE 基于普通 HTTP，浏览器自带断线重连和 Last-Event-ID 续传，更简单。
- **为什么事件流不用进程内的 channel 广播？** 数据库才是事实来源。直接从数据库按 ID 分页读，断线重连、进程重启都不会漏事件，也不会推送一个最终回滚了的事件。
- **追问 Agent 为什么不能执行动作？** 执行权只能经过「诊断 → Guard → Policy → 审批」这条路。如果对话也能触发动作，就等于开了一条绕过闸门的后门。追问最多只能建议「补充证据」「重新诊断」「人工复核」，而且要由人点按钮，走正常流程。
