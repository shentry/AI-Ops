# 验证状态机：连续健康与复发观察

> 所属：[亮点五 · 恢复验证与经验沉淀](README.md)

## 一句话

验证分两个阶段。**verify 阶段**：窗口内连续 N 次健康才算恢复（passed），窗口结束时最后一次新鲜的观测不健康才算失败（failed），其余都是「无法判断」（inconclusive）。**watch 阶段**：恢复后继续观察，连续 N 次不健康算复发（recurred），观察到最后仍然健康才算稳定（stable）。

## 参数

```yaml
# 摘自 config.example.yaml（规则可以单独覆盖窗口）
remediation:
  verification:
    interval_seconds: 10    # 每 10 秒观测一次
    window_seconds: 300     # 验证窗口 5 分钟
    timeout_seconds: 5      # 单次观测超时 5 秒（必须 < 30 秒）
    required_passes: 3      # 连续 3 次健康才算恢复；watch 阶段连续 3 次不健康算复发
    watch_seconds: 1800     # 恢复后观察 30 分钟；为 0 则不观察
```

启动时会校验：`0 < 超时 < 间隔 < 窗口`，并且 `(连续次数 - 1) × 间隔 < 窗口`，否则在窗口内根本不可能凑够连续次数。配置注释写明，这些是**待演练校准的初值**。

## 先弄懂：「连续」和「新鲜」

- **连续**：中间不能有任何一次不健康或看不到。健康、健康、看不到、健康，只算 1 次连续。
- **新鲜**：两次观测的间隔不能太长（超过间隔的阈值就算不新鲜）。比如 worker 卡了 2 分钟，第 2 次观测和第 1 次之间就断了，第 1 次的健康不能和第 2 次连起来。

```go
// 连续计数的核心逻辑（摘自 evaluateVerification，有删减）
if observation.Observation == "healthy" {
	passes := task.ConsecutivePasses + 1
	if !spec.ObservationFresh(task.LastCheckedAt, now) {
		passes = 1 // 和上一次隔得太久：从头计数
	}
	if passes >= spec.RequiredPasses {
		result.Status = "passed"
		return result
	}
}
// 不健康或看不到：连续计数在存储层被重置为 0
```

## verify 阶段的判定

```go
// 摘自 internal/diagnose/verification_worker.go（有删减）
// 只有窗口内凑够连续健康次数才算通过，迟到的结果永远不会被判为通过。
// 窗口到期时，只有「截止前最后一次、仍然新鲜的观测是不健康」才判失败；
// 健康次数没凑够的，判为无法判断，而不是恢复
func evaluateVerification(task store.VerifyTask, spec incident.VerificationSpec, now time.Time, observation *VerificationObservation) store.VerificationCompletion {
	result := store.VerificationCompletion{CheckedAt: now, Status: "inconclusive", Observation: "unavailable",
		Detail: "verification window expired without a fresh unhealthy observation"}
	interval := time.Duration(spec.IntervalSeconds) * time.Second
	if !now.Before(task.DeadlineAt) { // 窗口已结束
		last := task.LastCheckedAt
		if last != nil && last.Before(task.DeadlineAt) && now.Sub(*last) <= interval {
			var previous VerificationObservation
			if json.Unmarshal(task.LastResultJSON, &previous) == nil && previous.Observation == "unhealthy" {
				result.Status, result.Observation = "failed", "unhealthy" // 有确凿的「不健康」证据
			}
		}
		return result // 否则 inconclusive
	}
	// 窗口内：累计连续健康（见上面），够了就 passed
	// ……
	result.Status = "pending"
	result.NextCheckAt = nextCheck(now, interval, task.DeadlineAt) // 预约下一次观测
	return result
}
```

判定表：

| 情况 | 结论 | 理由 |
|---|---|---|
| 窗口内凑够连续 N 次健康 | **passed** | 有稳定的健康证据 |
| 窗口结束，最后一次新鲜观测是不健康 | **failed** | 有确凿的失败证据 |
| 窗口结束，健康次数没凑够 | inconclusive | 有健康迹象，但不够稳定 |
| 窗口结束，最后的观测是看不到，或者不新鲜 | inconclusive | 没有证据 |
| 窗口结束后才到的健康结果 | inconclusive | 迟到的结果不算 |

**为什么「失败」也要求确凿证据？** 失败会触发补偿和重诊，这些都是新的动作。如果因为「看不到」就判失败，监控一抖就会引发一连串不必要的处置。

## watch 阶段：识别复发

verify 阶段 passed 之后，如果配置了观察期，任务**不结束**，而是转入 watch 阶段：

```go
// 摘自 internal/store/verification.go 的 FinalizeVerification（有删减）
watching := c.Status == "passed" && snapshot.Verification.WatchSeconds > 0
if watching {
	updates["status"], updates["phase"], updates["consecutive_failures"] = "pending", "watch", 0
	updates["next_check_at"] = now.Add(interval)
	updates["deadline_at"] = now.Add(time.Duration(snapshot.Verification.WatchSeconds) * time.Second)
}
```

```go
// 摘自 internal/diagnose/verification_worker.go 的 evaluateWatch（有删减）
func evaluateWatch(task store.VerifyTask, spec incident.VerificationSpec, now time.Time, observation *VerificationObservation) store.VerificationCompletion {
	if !now.Before(task.DeadlineAt) { // 观察期结束
		if 最后一次观测新鲜且健康 {
			return store.VerificationCompletion{Status: "stable", Detail: "no recurrence during the watch window"}
		}
		return store.VerificationCompletion{Status: "inconclusive", Detail: "watch window ended without a fresh healthy observation"}
	}
	// 观察期内：任何一次看不到或不新鲜 → 立刻判为无法确认稳定
	if !spec.ObservationFresh(task.LastCheckedAt, now) || observation.Observation == "unavailable" {
		return store.VerificationCompletion{Status: "inconclusive", Detail: "watch observations are incomplete; stability cannot be confirmed"}
	}
	// 连续 N 次不健康（和证明恢复用的次数相同）→ 复发
	if observation.Observation == "unhealthy" && task.ConsecutiveFailures+1 >= spec.RequiredPasses {
		return store.VerificationCompletion{Status: "recurred"}
	}
	return /* pending，预约下一次 */
}
```

| 结局 | 条件 | 后果 |
|---|---|---|
| **stable** 稳定 | 观察期结束，最后一次新鲜观测健康 | 条件满足时写入故障记忆 |
| **recurred** 复发 | 连续 N 次不健康 | 打开 critical 级问题 `recurred`，升级给人，阻断规则 |
| inconclusive | 观察有缺口 | 打开问题 `verify_inconclusive`，阻断规则 |

**为什么要有观察期？** 有些「修好」只是暂时的：比如内存泄漏的服务重启后会好一阵子，半小时后又挂。没有观察期，这种情况会被记成「重启有效」，甚至写进故障记忆，下次继续用。

## 一次完整验证的时间线

以重启为例：

| 时刻 | 观测 | 连续次数 | 状态 |
|---|---|---|---|
| 10:05:00 | 执行完成，创建任务 | — | pending（截止 10:10:00） |
| 10:05:00 | 容器刚启动，探针失败 | 0 | pending |
| 10:05:10 | 全部健康 | 1 | pending |
| 10:05:20 | 全部健康 | 2 | pending |
| 10:05:30 | 全部健康 | 3 | **passed** → 进入 watch（截止 10:35:30） |
| 10:05:40 ～ 10:35:30 | 每 10 秒一次，全部健康 | — | pending |
| 10:35:30 | 观察期结束，最后一次健康 | — | **stable** |

## 存储层再校验一次

worker 算出的结论，提交时要在锁内再过一遍：

```go
// 摘自 internal/store/verification.go 的 FinalizeVerification（有删减）
if c.Status == "passed" && (!now.Before(task.DeadlineAt) || c.Observation != "healthy") {
	c.Status = "inconclusive" // 窗口外的健康不能算通过
}
if c.Status == "passed" && passes < snapshot.Verification.RequiredPasses {
	return errors.New("store: passed verdict without the required consecutive healthy observations")
}
if c.Status == "failed" && /* 窗口内，或者最后一次不新鲜，或者不是 unhealthy */ {
	c.Status = "inconclusive" // 没有新鲜的不健康证据，不能判失败
}
```

同时还会重新检查：审批单的 hash 和状态、故障范围是否仍在规则内。**worker 算错了也写不进去**，这是双保险。

## 认领和停机

- 验证任务也是「表 + 认领」模式：`claimed_at` 记录认领时间，超过租约（30 秒）没完成就重新入队。
- 提交时带着认领时间做条件更新（`WHERE claimed_at = ?`），过期的认领写不进去。
- **停机不算一次观测**：进程收到停止信号时，正在进行的观测直接放弃，不写任何结论，等重启后由租约恢复继续。截止时间保持原样。

## 常见追问

- **复发需要连续 N 次不健康，为什么不是 1 次？** 和恢复用同样的标准才公平：一次抖动不能证明复发，就像一次健康不能证明恢复。
- **观察期能不能关掉？** 能，`watch_seconds: 0`。那样 passed 就是终态，也会触发记忆写入。但 auto 规则要求保留观察窗。
- **验证期间又来了新告警怎么办？** 每次观测前都会重新检查故障范围（观察期除外）。范围变了，就判为 inconclusive，因为验证的前提已经不成立。
