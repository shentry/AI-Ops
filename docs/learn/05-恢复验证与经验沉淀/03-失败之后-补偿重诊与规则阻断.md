# 失败之后：补偿、重诊与规则阻断

> 所属：[亮点五 · 恢复验证与经验沉淀](README.md)

## 一句话

验证失败（或无法判断）之后，系统在**同一个事务里**做四件事：打开待处理问题、执行预先冻结的补偿、发起有上限的自动重诊（仅在确认失败时）、如果方案来自记忆就降级记忆。同时，失败会**阻断**这条规则的后续自动执行，直到有人复核并重置。

## 先弄懂：「描述效果」和「执行效果」分开

验证 worker 只负责**判断**。判断之后要做的事（重诊、降级记忆、写记忆），它只**描述**，不执行：

```go
// 摘自 internal/diagnose/verification_worker.go（有删减）
// prepareEffects 只描述要做的效果，从不执行它们。
// 由存储层把这些效果和裁决、审计、统一的重诊准入放在同一个事务里执行。
// 补偿动作没有任何效果：它从不重诊、不写记忆、不降级
func (w *VerificationWorker) prepareEffects(ctx context.Context, approval store.Approval, snapshot incident.ExecutionContext, completion *store.VerificationCompletion) error {
	if snapshot.Kind != incident.KindPrimary {
		return nil
	}
	if completion.Status == "failed" {
		completion.Retry = true // 请求重诊
		if run.Mode == "memory_hit" {
			completion.DemoteFingerprint = fingerprint // 请求降级记忆
		}
		return nil
	}
	// stable（或没有观察期的 passed）：满足条件时附上记忆候选（下一篇）
	// ……
}
```

为什么要这样拆？如果 worker 先发起重诊，再提交裁决，两步之间崩溃，就会出现「重诊排上了，裁决却没记下」。所有效果和裁决在一个事务里，要么都发生，要么都不发生。

## 失败之后的四件事

```go
// 摘自 internal/store/verification.go 的 FinalizeVerification（有删减）
if c.Status == "failed" || c.Status == "inconclusive" {
	// ① 打开问题：verify_failed 或 verify_inconclusive
	openIncidentProblem(ctx, tx, IncidentProblem{Code: "verify_" + c.Status /* … */})
	// ② 如果快照里带了补偿，排队执行
	if invalid == nil && snapshot.Compensation != nil {
		id, _ := queueCompensation(ctx, tx, approval, snapshot, c.Status, now)
		final.CompensationID = id
	}
}
if c.Status == "failed" {
	// ③ 记忆降级（仅当方案来自记忆）
	if c.DemoteFingerprint != "" {
		(&DB{DB: tx}).DemoteFaultMemory(ctx, c.DemoteFingerprint, now)
	}
	// ④ 自动重诊
	if c.Retry {
		requestVerificationRetry(ctx, tx, approval, parent, c.Detail, now, &final)
	}
}
```

| | failed（确认失败） | inconclusive（无法判断） |
|---|---|---|
| 打开问题 | `verify_failed` | `verify_inconclusive` |
| 补偿 | 有就执行 | 有就执行 |
| 自动重诊 | **是** | 否（没有确凿证据，不该自动再做一次） |
| 记忆降级 | 方案来自记忆时降级 | 否 |
| 阻断规则 | 是 | 是 |
| 通知人 | 是 | 是 |

## 补偿：预先冻结的「撤销」

补偿是**在批准主动作时就一起冻结**的撤销方案。目前只有「隔离上游账号」有补偿（恢复调度），而且要求规则里配置了 `compensate: true`。

```go
// 摘自 internal/store/verification.go 的 queueCompensation（有删减）
// 把失败动作的冻结撤销方案发布成一张「已批准」的补偿审批单
func queueCompensation(ctx context.Context, tx *gorm.DB, parent Approval, snapshot ExecutionContext, status string, now time.Time) (uint64, error) {
	plan := snapshot.Compensation
	compensation := ExecutionContext{
		Version: ExecutionContextVersion, Kind: KindCompensation, Service: snapshot.Service,
		Rule: snapshot.Rule, Target: snapshot.Target, /* 动作、参数、revision、检查项都取自冻结的补偿方案 */
		ExpiresAt: now.Add(CompensationTTL), // 15 分钟内必须执行
	}
	// 写入一张 approved 状态的审批单，parent_approval_id 指向主动作
	// 同一事务追加 compensation.queued 事件
}
```

关键设计：

- **授权是预先给的**：人批准隔离时，同时批准了「失败就撤销」。补偿不需要再等人批准，否则会卡在「做了一半」的状态。
- **只撤销自己写的值**：执行补偿时，账号的状态必须仍是「我们写入的不可调度」。如果别人已经手动改过，补偿不会覆盖人的操作。
- **补偿自己也要验证**：它同样有冻结的检查项。补偿没通过验证，直接升级给人。
- **补偿不产生连锁效果**：不重诊、不写记忆、不降级，避免补偿引发新一轮自动处置。

## 自动重诊：有上限

```go
// 摘自 internal/store/verification.go（有删减）
func requestVerificationRetry(ctx context.Context, tx *gorm.DB, approval Approval, parent Incident, detail string, now time.Time, final *VerificationFinalization) error {
	run, created, err := requestRun(ctx, tx, RunRequest{
		IncidentID: parent.ID, Mode: ModeFull,  // 重诊用 full 模式
		Trigger: RunTriggerRetry, RetryOf: &approval.RunID, // 记下「是哪次诊断失败了」
		Reason: detail, RequestedAt: now,
	})
	var refusal *RunAdmissionError
	if refusal != nil && refusal.Code != "active_processing" {
		// 重诊被拒绝（比如次数用完）：打开 critical 级问题，交给人
		openIncidentProblem(ctx, tx, IncidentProblem{Code: "manual_check", Severity: "critical",
			Summary: "automatic retry stopped: " + refusal.Code /* … */})
	}
	// ……
}
```

重诊走的是和告警入口、人工重诊**同一个准入函数** `requestRun`（亮点一第 5 篇）。上限由 `retry_of` 链的长度决定：

```text
原始诊断 R0 → 验证失败 → 重诊 R1（retry_of=R0）   ✓ 允许
R1        → 验证失败 → 重诊 R2（retry_of=R1）   ✓ 允许
R2        → 验证失败 → 重诊 R3？                ✗ 链深度超过 2，拒绝 → 转人工
```

**重诊和普通诊断有什么不同？**

- 不查故障记忆：上次的方案刚刚失败，不能再从记忆里取同样的方案。
- 证据前面会注入上一轮的根因、计划和验证失败详情，并明确写着「不要复用计划，仅供对照」（亮点二）。

## 规则阻断：失败的规则不能再自动执行

```go
// 摘自 internal/store/remediation.go
// 这些持久化的事实会阻断一条规则后续的自动主动作，直到操作人重置它：
// 执行失败或结果未知、恢复验证失败或无法判断、复发，以及复盘时被判为错误的动作
var blockingEvents = []string{
	"execution.failed", "verify.failed", "verify.inconclusive", "verify.recurred",
}
// 另外：review.recorded 事件中 phase=action、status=wrong（人工复盘判定动作错误）
```

计算规则状态时，查找「这条规则最近一次重置之后，有没有阻断事件」：

- 有 → `state.Blocked` 非空；
- Policy 把这条规则的 auto 决策**降级为人工**（亮点三）；
- 执行器认领时，拒绝被阻断的 auto 审批（亮点四）；
- 人复核之后，调用 `/api/v1/remediation/rules/:rule/reset` 重置。重置本身是一条控制事件，有记录。

**为什么阻断的是规则，而不是 incident？** 失败说明「这条规则在这类故障上的做法」出了问题，下一个 incident 大概率也会遇到。阻断规则可以让人在它再次自动执行之前先复核。manual 模式不受影响，因为本来就有人把关。

## 通知

需要人关注的结局，都会通过发件箱通知（亮点六）：`verify.failed`、`verify.inconclusive`、`verify.recurred` 事件本身就会触发通知任务。passed 和 stable 也会发一条「恢复验证结果」通知；排了补偿时，通知里会注明补偿审批单的编号。

## 常见追问

- **重启没有补偿，失败了怎么办？** 重启没法撤销。失败后会自动重诊，并阻断规则；重诊给出的新建议需要人批准。
- **inconclusive 为什么也要执行补偿？** 看不清的时候，撤销一个可以撤销的动作是更保守的选择：隔离上游会减少可用容量，看不清效果时恢复原状更安全。
- **为什么重诊的上限是 2 次？** 两次不同的方案都没解决，说明问题超出了自动处置的能力，继续自动尝试的收益很低，风险却在累积。
