# 亮点五：恢复验证与经验沉淀

> 返回：[知识库首页](../README.md)

## 一句话（简历写法）

把「执行成功」「业务恢复」「告警结束」拆成三个独立事实，用持久化的验证任务驱动恢复判定。按快照里冻结的检查项（容器状态、健康检查、业务探针、错误率）定时观测，窗口内**连续 N 次健康**才算恢复，之后进入观察期识别复发。验证失败时，在同一事务里执行预先冻结的补偿、发起有上限的自动重诊、阻断规则的后续自动执行；只有稳定恢复的方案才写入故障记忆。

## 它解决什么问题

- 命令执行成功，业务却没恢复：重启了，但数据库还是挂的。
- 偶然一次健康就宣布恢复，其实服务还在抖动。
- 修好了没多久又复发，没人知道。
- 失败之后怎么办：撤销？重试？同样的动作还能自动做吗？
- 什么样的经验值得记住，记住之后怎样才不会出事。

## 方案全景

```text
FinishExecution(executed) → verify_task { phase=verify, 截止时间=现在+窗口 }
                                  │
VerificationWorker（每秒一轮，只读，不调模型）
  认领一个到期的任务 → 校验快照（hash、版本、故障范围）
  → Verifier.Check：执行冻结的检查项（容器 / health / 业务探针 / 错误率 / 账号 / 分组）
  → 判定 → FinalizeVerification（锁内再校验一次，原子提交裁决和后续效果）

verify 阶段：连续 3 次健康 ─▶ passed ─▶ 进入 watch 阶段（30 分钟）
            窗口结束时最后一次新鲜观测不健康 ─▶ failed
            其他（缺数据、次数不够、迟到的结果）─▶ inconclusive
watch 阶段：连续 3 次不健康 ─▶ recurred（复发）
            结束时最后一次新鲜观测健康 ─▶ stable
            观测有缺口 ─▶ inconclusive

failed       ─▶ 补偿 + 自动重诊（最多 2 次）+ 记忆降级 + 阻断规则 + 通知
inconclusive ─▶ 补偿 + 阻断规则 + 通知人
recurred     ─▶ 阻断规则 + 升级给人
stable       ─▶ 条件满足时写入故障记忆
```

## 读完本亮点你会知道

- 为什么执行成功不等于修好，三个事实分别由谁判定。
- 验证状态机的每一种转换，「连续」和「新鲜」分别是什么意思。
- 失败之后的补偿、重诊、阻断分别在什么条件下发生。
- 故障记忆的写入门槛、命中后的处理，以及它的边界。

## 面试怎么讲

**30 秒版本：**
我们把「动作执行成功」和「业务恢复」当成两个独立的事实。执行成功后创建一个持久化的验证任务，验证 worker 只读、不调模型，按审批时冻结的检查项定时观测，比如容器确实重启过、健康检查通过、真实调一次上游模型成功。窗口内连续 3 次健康才判定恢复；缺数据不算健康，窗口结束后才到的结果也不算。恢复后再观察 30 分钟，看是否复发。失败时，在同一个事务里执行预先冻结的补偿、发起有上限的自动重诊，并阻断这条规则的后续自动执行，直到人来复核。

**常见追问：**

- **为什么要「连续」3 次？** 一次健康可能是偶然的，比如刚重启时进程还没完全挂掉。连续多次健康才能说明稳定，这和告警规则里的 `for: 1m` 是同样的道理。
- **缺数据为什么不算健康？** 缺数据说明「看不到」，不说明「没问题」。如果把看不到当成健康，监控一挂，所有验证都会通过。
- **为什么验证失败了还要阻断规则，而不是让重诊继续自动执行？** 规则的动作刚刚被证明没用。重诊可以给出新建议，但再自动执行一次同类动作，很可能是在重复错误，所以降为人工。
- **验证通过了，为什么不直接关 incident？** incident 的状态由告警源决定。业务恢复了，告警未必马上恢复；告警恢复了，也可能只是暂时的。两个事实各自由自己的来源判定，互不代替。
