# 故障记忆：只记验证过的成功

> 所属：[亮点五 · 恢复验证与经验沉淀](README.md)

## 一句话

同类故障（同一分组 + 同一告警）如果曾经被**高置信度诊断、Guard 未改写、验证稳定恢复**的方案解决过，就把这个方案记下来。下次命中时跳过大模型（0 次模型调用），但取证、Guard、规则授权、审批、验证**一步不少**。命中的方案验证失败，就立刻降级。

## 先弄懂：记住 ≠ 学会

「把成功案例存进库里」只能提高可检索性，排除不了三种情况：

1. **偶然成功**：这次碰巧好了，其实不是动作的功劳；
2. **过期规则**：以前有效，现在环境变了；
3. **错误归因**：好了，但原因和记下的根因无关。

所以本项目的记忆设计围绕三个问题：**什么时候写**、**命中后怎么用**、**错了怎么纠正**。

## 故障指纹

```go
// 摘自 internal/incident/execution.go
func FaultFingerprint(groupKey, alertName string) string
// 取 incident 的分组键 + 首条告警名，计算摘要
```

同一个服务（分组键 `sub2api`）的同一种告警（`Sub2APIDown`）就是同一类故障。诊断时用 incident 的首条告警名，验证时用快照里冻结的 `FaultAlert`，两边来源一致。

## 什么时候写：门槛很高

写入只发生在验证事务里，必须**同时**满足：

| 条件 | 为什么 |
|---|---|
| 验证结果是 stable（或没有观察期时的 passed） | 排除偶然成功和很快复发的情况 |
| 是主动作，不是补偿 | 补偿是撤销，不是解决方案 |
| 原诊断不是重诊 | 重诊说明前一次失败过，归因不够干净 |
| 原诊断不是记忆命中 | 避免记忆自我强化 |
| 原诊断的 `plan.confidence = high` | 模型本身也有把握（只是条件之一，不是唯一依据） |
| Guard 的审计步骤明确是「allow，未改写」 | 执行的就是模型原本的方案，而不是被规则修正过的 |

```go
// 摘自 internal/diagnose/verification_worker.go 的 prepareEffects（有删减）
remember := completion.Status == "stable" || (completion.Status == "passed" && snapshot.Verification.WatchSeconds == 0)
if run.RetryOf != nil || run.Mode == "memory_hit" || run.PlanJSON == nil {
	return nil
}
if plan.Confidence != "high" {
	return nil
}
if !hasExplicitUnchangedGuard(steps) { // 要求 Guard 步骤的输出以 "decision=allow overridden=false" 开头
	return nil
}
completion.Memory = &store.FaultMemory{Fingerprint: fingerprint, RCAText: rca, PlanJSON: *run.PlanJSON,
	Confidence: "high", LastSuccess: completion.CheckedAt, TTLSeconds: w.memoryTTLSeconds /* … */}
```

`hasExplicitUnchangedGuard` 要求 Guard 步骤**存在、成功完成**，而且输出**以完整的固定前缀开头**，不是在文本里搜子串。缺失 Guard 记录，永远不被当成 allow。

## 命中之后怎么用

```go
// 摘自 internal/memory/store.go（有删减）
func (s *Store) Lookup(ctx context.Context, fingerprint string) (store.FaultMemory, bool, error) {
	entry, err := s.db.GetFaultMemory(ctx, fingerprint)
	if errors.Is(err, store.ErrMemoryNotFound) {
		return store.FaultMemory{}, false, nil
	}
	if s.onlyHighConfidence && entry.Confidence != "high" {
		return store.FaultMemory{}, false, nil
	}
	// 有效期从「上次验证成功」算起（默认 1 小时）
	if entry.LastSuccess.Add(time.Duration(s.ttlSeconds) * time.Second).Before(time.Now().UTC()) {
		return store.FaultMemory{}, false, nil
	}
	s.db.TouchFaultMemory(ctx, fingerprint, time.Now().UTC()) // 记录命中次数
	return entry, true, nil
}
```

命中后的流水线（亮点二第 6 篇）：

```text
1 记忆查找 ── 命中 ─▶ rca、plan 取自记忆，run.mode 改为 memory_hit
2 证据采集 ── 照常 ─▶ Guard 只信本次的事实
3 推理 ────── 跳过（0 次模型调用）
4 Guard ──── 照常：用当前事实复核记忆里的 plan
5 Policy ─── 照常：规则授权、冻结快照
   审批 ─── 照常：manual 规则仍然要人批准
   执行、验证 ─ 照常
```

**记忆只是省掉了「想」，没有省掉「管」和「判」。** 记忆从来不构成执行许可。

## 错了怎么纠正

- **命中的方案验证失败** → 同一事务里降级这条记忆（`DemoteFaultMemory`），并发起重诊。
- **重诊不查记忆** → 不会陷入「坏记忆 → 失败 → 重诊 → 又命中坏记忆」的循环。
- **有效期到了** → 自然失效，下次重新走模型诊断。

## 另一种经验：执行历史

除了故障记忆，还有一张只追加的执行历史表 `fault_cmd_history`：每次主动作执行（不含 aborted），都记下动作、参数、结果摘要。

记忆**没命中**时，同类故障最近 5 条执行历史会注入证据前面：

```text
# 历史命令（同类故障曾被审批执行过，仅供参考，不构成权限依据）
- tool=docker_restart args={"container":"sub2api"} result=executed: restarted container sub2api at=2026-09-20T03:12:00Z
```

它是**原始证据**，只追加、不修改；故障记忆是**派生知识**，可以覆盖、会过期、会降级。两者分开存放，正是「原始证据和可修订的经验分开」的做法。

## 边界：这是缓存，不是学习

按 Agent 工程对「持续进化」的标准，真正的学习需要：跨多个案例归纳出规律，用未参与归纳的案例验证，同时确认旧能力没有退化。本项目的故障记忆**没有做到这些**：

- 它按指纹精确匹配，是「验证过的方案缓存」，不做跨案例归纳；
- 有命中、未命中、过期、降级计数，但没有评估「命中后是否真的更好」；
- 记忆命中时，报告里的 RCA 是上次写下的文字，不是按本次证据重新推导的。

这是有意的取舍：在自动处置场景里，一个保守、可解释、错了能立刻撤回的缓存，比一个复杂但难以验证的「学习」机制更可控。

## 常见追问

- **记忆有效期为什么只有 1 小时？** 默认值偏保守：环境变化快，过期的记忆比没有记忆更危险。它可以配置。
- **记忆命中能让 manual 规则变成自动执行吗？** 不能。记忆只替代模型的推理，授权仍然只看规则。
- **为什么不用向量库做相似故障检索？** 这里的「同类故障」有明确定义（分组键 + 告警名），精确匹配就够了。相似度检索会引入「看起来像但其实不一样」的风险，而且相似度不是执行许可。
