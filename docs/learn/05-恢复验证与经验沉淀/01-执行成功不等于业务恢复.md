# 执行成功不等于业务恢复

> 所属：[亮点五 · 恢复验证与经验沉淀](README.md)

## 一句话

「重启命令返回成功」只说明写操作生效了，不说明业务恢复了。本项目把三件事拆成三个独立的事实，各有各的状态、各由各的来源判定：**执行结果**（审批单）、**业务恢复**（验证任务）、**告警状态**（incident）。

## 先弄懂：什么叫「完成证据」

Agent 工程里有一条基本原则：**完成要由能从环境里读出来的证据来判定**。比如「退款记录已经落库」比「模型说退款成功」可靠。

放到运维场景：

| 说法 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 模型说「重启后应该能恢复」 | 什么也证明不了 | — |
| Docker 返回「重启成功」 | 容器重启了 | 进程能正常服务 |
| `/health` 返回 200 | 进程在响应 | 能处理真实请求（sub2api 的 `/health` 不检查依赖） |
| 业务探针成功 | 一次真实请求走通了 | 持续稳定 |
| 错误率低于阈值 | 真实流量基本正常 | 流量太少时说明不了问题 |
| **窗口内连续多次上述检查都通过** | **业务恢复了** | 之后会不会复发 |
| **观察期内没有复发** | **修复是稳定的** | — |

## 三个独立的事实

| 事实 | 存在哪里 | 由谁判定 | 状态 |
|---|---|---|---|
| 动作是否写成功 | `approval.status` | 执行器 + 对账（亮点四） | executed / aborted / failed |
| 业务是否恢复 | `verify_task` | 验证 worker，读真实环境 | passed / failed / inconclusive → stable / recurred |
| 告警是否结束 | `incident.status` | 告警源推送的 resolved（亮点一） | firing → resolved |

它们**互不代替**：

- 执行成功 → 只是创建验证任务；
- 验证通过 → 通知里写的是「业务恢复验证连续通过；告警状态仍由告警源同步」，**不会**替告警源关单；
- 告警恢复 → 不代表验证通过，验证任务照常继续。

效果报表里的「无人介入恢复」，要求验证稳定**并且**原始告警已恢复，两个事实都满足才算。

## 验证标准在批准时就定好了

恢复标准是在 `Action.Prepare` 阶段**由动作自己决定**、冻结进快照、和动作一起被批准的：

| 动作 | 冻结的检查项 |
|---|---|
| 重启 | 容器检查（同一个 ID，在快照之后重启过，正在运行）+ `/health` + 业务探针 |
| 回退 | 容器检查（运行的镜像摘要是目标版本）+ `/health` + 错误率 + 业务探针 |
| 隔离上游 | 账号检查（已不可调度）+ 分组检查（仍有足够可用账号）+ 错误率 |

为什么要在批准时就定？如果执行之后再决定「怎样算修好」，就可能被有意无意地放宽标准，比如只看 `/health`。**验证标准也是批准内容的一部分，被 plan_hash 覆盖。**

## 验证器：权限最小的观测者

```go
// 摘自 internal/diagnose/verify.go（有删减）
// Verifier 对快照里冻结的检查项做一次有界的只读观测。
// 它没有数据库、没有写动作、不调模型，也无权宣布最终结论。缺数据是 "unavailable"，永远不是健康
type Verifier struct {
	registry   *tools.Registry // 只读工具（docker_inspect、Prometheus）
	httpClient *http.Client
	accounts   AccountReader   // sub2api 只读接口
	probe      *sub2api.Probe  // 业务探针
}

func (v *Verifier) Check(ctx context.Context, snapshot incident.ExecutionContext, remaining time.Duration) VerificationObservation {
	spec := snapshot.Verification
	// 单次检查超时不能超过 30 秒，也不能超过窗口剩余时间
	checkCtx, cancel := context.WithTimeout(ctx, min(time.Duration(spec.TimeoutSeconds)*time.Second, remaining))
	defer cancel()
	result := VerificationObservation{Observation: "healthy"}
	for _, check := range spec.Checks {
		observation := v.check(checkCtx, check)
		switch {
		case observation.Observation == "unavailable":
			result.Observation = "unavailable" // 任何一项看不到 → 整体看不到
		case observation.Observation == "unhealthy" && result.Observation == "healthy":
			result.Observation = "unhealthy"   // 任何一项不健康 → 整体不健康
		}
	}
	return result
}
```

一次观测的结果只有三种：**healthy**（全部健康）、**unhealthy**（至少一项不健康）、**unavailable**（至少一项看不到）。unavailable 的优先级最高：只要有一项看不到，就不能下「健康」或「不健康」的结论。

看几个检查项的判定细节：

```go
// 摘自 internal/diagnose/verify.go（有删减）

// 容器检查
case p.ID != "" && live.ID != p.ID:
	return observed("unhealthy", "container %s is a different instance", p.Name)
case !live.Running || live.Restarting:
	return observed("unhealthy", "container %s is %s", p.Name, live.Status)
case !p.StartedAfter.IsZero() && !live.StartedAt.After(p.StartedAfter):
	return observed("unhealthy", "container %s has not restarted since the snapshot", p.Name)

// 业务探针：连接都失败（状态码 0）是看不到；拿到非 200 才是不健康
case result.OK:
	return observed("healthy", "probe %s in %s", result.Detail, result.Latency)
case result.StatusCode == 0:
	return observed("unavailable", "%s", result.Detail)
default:
	return observed("unhealthy", "probe %s", result.Detail)

// 错误率：真实请求太少，不算通过，因为还没有恢复的证据
if requests < float64(p.MinRequests) || requests == 0 {
	return observed("unavailable", "only %.0f requests in 5m, need %d", requests, p.MinRequests)
}
if ratio > p.MaxRatio {
	return observed("unhealthy", "error ratio %.3f above %.3f", ratio, p.MaxRatio)
}
```

**业务探针**是一次真实的请求：用专用测试密钥，通过 sub2api 网关调用一次上游模型，只要 1 个输出 token。它要求 HTTP 200 并且拿到完整的模型响应。每次调用都会真实计费，所以频率受验证间隔限制，响应内容也不会保存。这是唯一能证明「网关真的能转发请求」的检查。

## 常见追问

- **既然有业务探针，为什么还要看容器和 `/health`？** 它们回答不同的问题：容器检查确认「重启真的发生了、是同一个实例」；`/health` 便宜、快；探针最接近真实，但有成本。组合起来，任何一项不满足都能定位到具体原因。
- **验证 worker 为什么不调模型？** 验证只需要判断「这些检查通过了吗」，完全可以用确定性代码做。让模型参与判定，会重新引入它自己的不确定性。
