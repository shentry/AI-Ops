# 人工审批：飞书卡片与有效期

> 所属：[亮点三 · 确定性闸门与规则授权](README.md)

## 一句话

manual 规则产生的审批单会以飞书卡片的形式推给值班群，卡片上的「批准」「拒绝」按钮都带着审批 ID 和 plan_hash。回调时依次检查：事件是否已处理过、操作人是否在白名单里、hash 是否一致、审批单是否仍待批准、是否过期。审批单默认 30 分钟后过期，过期即失效，沉默不等于同意。

## 审批单的状态机

```text
                       Policy 通过
                 ┌─────────┴──────────┐
            manual 规则             auto 规则
                 │                    │
                 ▼                    │
            ┌─────────┐               │
            │ pending │──── 超时 ─────┼──▶ expired
            └─────────┘               │
             │       │                │
          人批准   人拒绝              │
             │       └──▶ denied       │
             ▼                        ▼
         ┌──────────┐  认领时发现条件不满足
         │ approved │ ────────────────────▶ expired
         └──────────┘
             │ 执行器认领
             ▼
        ┌───────────┐
        │ executing │
        └───────────┘
          │    │    │
          ▼    ▼    ▼
    executed aborted failed          （执行细节见亮点四）
```

## 审批单怎么生成

```go
// 摘自 internal/approval/service.go 的 Prepare（有删减）
// 只校验、构造草稿，不写库。草稿由 CompleteRun 和诊断结论一起原子发布
func (s *Service) Prepare(incidentID, runID uint64, decision Decision, reason string) (store.Approval, error) {
	snapshot, err := incident.ParseExecutionContext(decision.ExecutionContext)
	hash, err := incident.PlanHash(decision.ToolName, decision.Args, decision.ExecutionContext)
	if err != nil || hash != decision.PlanHash {
		return store.Approval{}, fmt.Errorf("approval: plan hash does not match execution content")
	}
	// 决策类型必须和快照里的规则模式一致：不能出现「auto 决策 + manual 规则」
	if (decision.Kind == DecisionAuto) != (snapshot.Rule.Mode == incident.ModeAuto) {
		return store.Approval{}, fmt.Errorf("approval: decision contradicts rule mode")
	}
	draft := store.Approval{IncidentID: incidentID, RunID: runID, ToolName: decision.ToolName,
		ArgsJSON: decision.Args, ExecutionContext: decision.ExecutionContext,
		PlanHash: hash, Status: "pending", ExpiresAt: snapshot.ExpiresAt /* … */}
	if decision.Kind == DecisionAuto {
		// auto：批准人就是规则本身
		actor, source := "system:rule:"+*draft.RuleID, "rule"
		draft.Status, draft.DecidedBy, draft.DecisionSource = "approved", &actor, &source
	}
	return draft, nil
}
```

## 飞书卡片上有什么

诊断报告卡片包含：根因、置信度、建议动作、Guard 和 Policy 的结论，以及一个「打开 Web 控制室」按钮。如果有待审批的单子，还会有两个回调按钮：

```go
// 摘自 internal/notify/feishu/card.go
func ApprovalButton(action, label string, approvalID uint64, planHash, buttonType string) map[string]any {
	return map[string]any{
		"tag":  "button",
		"text": map[string]any{"tag": "plain_text", "content": label},
		"type": buttonType,
		"behaviors": []any{map[string]any{
			"type": "callback",
			"value": map[string]any{
				"action":      action,     // approve / deny
				"approval_id": approvalID,
				"plan_hash":   planHash,   // 卡片展示的是哪一版，就带哪一版的 hash
			},
		}},
	}
}
```

一个细节：**只有当卡片上完整展示了动作、目标（含 ID）、规则、理由、hash、过期时间时，才显示「批准」按钮**；「拒绝」按钮始终显示。人只能批准自己完整看到的内容。

## 点了按钮之后

飞书把点击事件发到 `/integrations/feishu/events`。签名校验和解密由飞书官方 SDK 完成（见亮点七），然后进入业务处理：

```go
// 摘自 internal/notify/feishu/callback_business.go 的 CardAction（有删减）
eventID := cardEventID(event)
// ① 幂等：同一个事件（飞书可能重试推送）只处理一次
claimed, err := b.claimReceipt(ctx, eventID, /* … */)
if !claimed {
	return toast("success", "该操作已处理"), nil
}
// ② 权限：操作人必须在白名单里
if !b.allowed(operator) {
	return toast("error", "你没有审批权限"), nil
}
action, approvalID, planHash, err := cardActionValue(event)
approvalRow, err := b.approval.Get(ctx, approvalID)
// ③ 卡片展示的版本必须是当前版本
if approvalRow.PlanHash != planHash {
	return toast("error", "审批计划已变更，请刷新卡片"), nil
}
// ④ 只能处理待审批的单子
if approvalRow.Status != "pending" {
	return toast("success", "该审批已处理"), nil
}
// ⑤ 真正的决策：在数据库事务里再核对一遍
decided, err := b.approval.Decide(ctx, approvalID, action == "approve", planHash, "feishu:"+operator, "", "feishu")
if errors.Is(err, store.ErrApprovalConflict) {
	return toast("error", "审批已变更、过期或已处理，请刷新卡片"), nil
}
b.patchDecisionAsync(decided, cardMessageID(event), approve) // 异步把卡片更新为「已批准 / 已拒绝」
```

第 ⑤ 步的数据库事务：

```go
// 摘自 internal/store/approval.go 的 decideApprovalInTx（有删减）
tx.Clauses(clause.Locking{Strength: "UPDATE"}).First(&approval, id) // 锁住审批单
if approval.Status != "pending" || !approval.ExpiresAt.After(now) {
	return Approval{}, ErrApprovalConflict // 已处理或已过期
}
hash, err := incident.PlanHash(approval.ToolName, approval.ArgsJSON, approval.ExecutionContext)
if err != nil || expectedPlanHash == "" || hash != approval.PlanHash || hash != expectedPlanHash {
	return Approval{}, ErrApprovalConflict // 三方 hash 必须一致：请求带的、存储的、重新计算的
}
tx.Model(&Approval{}).
	Where("id = ? AND status = ? AND expires_at > ?", id, "pending", now). // 条件更新：再确认一次状态
	Updates(map[string]any{"status": status, "decided_by": decidedBy, "decided_at": now, "decision_source": decisionSource})
// 同一事务追加 approval.approved 或 approval.denied 事件
```

**为什么在内存里检查过了，事务里还要再查一遍？** 回调里的第 ③④ 步是为了尽早给用户友好的提示。但两次检查之间，另一个人可能刚好也点了按钮。只有数据库事务里加锁的检查才是最终裁决。

Web 控制台的审批接口（`POST /api/v1/approvals/{id}/approve`）走同一个 `Service.Decide`，同样必须带上 plan_hash。

## 有效期：沉默不等于同意

- 审批单默认 30 分钟过期（`approval.ttl_minutes`），过期时间冻结在快照里。
- `ExpiryWorker` 每分钟扫描一次：把过期的 pending 和 approved 单子置为 expired，写入 `approval.expired` 事件；快过期的单子会打开待处理问题 `approval_near_expiry`，提醒值班人员。
- `approval.expired` 属于「需要人关注」的事件，会自动推送通知。

为什么 approved 的单子也会过期？批准之后，执行器可能因为服务正忙等原因没能及时认领。拖了太久，现场早就变了，执行已经没有意义。

## 常见追问

- **两个人同时点「批准」会怎样？** 先到的事务拿到行锁并更新成功；后到的发现状态已经不是 pending，返回冲突，提示「已处理」。
- **飞书重复推送同一个回调会怎样？** `claimReceipt` 按事件 ID 记录回执，第二次直接返回「该操作已处理」，不会重复决策。
- **人拒绝之后会发生什么？** 审批单变成 denied，动作不会执行。incident 仍然开着，值班人员可以手动处理，或者在控制台发起重新诊断。
