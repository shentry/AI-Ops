# 亮点三：确定性闸门与规则授权

> 返回：[知识库首页](../README.md)

## 一句话（简历写法）

设计「模型提议、代码审核」的确定性闸门。Guard 只依据结构化证据检查动作前提并核实目标身份；处置规则是唯一的执行授权来源，按 observe / manual / auto 三种模式分级，自动执行在维护窗口、监控缺失、规则被阻断等情况下降级为人工。通过的动作被冻结成不可变快照，并用 plan_hash 绑定，保证人批准的就是最终执行的。

## 它解决什么问题

- **模型会犯错**：编造目标、以偏概全（把一条无关 OOM 当成根因）、被日志带偏。它自报的置信度也不可靠。
- **「允许重启」这句话太宽**：如果只按动作名授权，任何告警都可能触发重启。
- **批准与执行之间有时间差**：审批单可能被改，现场也可能变了。

## 方案全景

```text
模型的建议 Plan（只是数据）
      │
      ▼
 ┌─────────── Guard（diagnose/guard.go）───────────┐
 │ 只读本次证据的结构化事实，不读日志正文                │
 │ 公共规则：必须有真实目标；数据库或 Redis 挂了转人工    │
 │ 动作规则：重启 / 回退 / 隔离各自的前提               │
 │ 没写规则的动作一律拒绝                              │
 │ 不满足 → 动作改成 none（或转人工）                   │
 │ 满足   → 输出由证据确认的目标身份（容器 ID 等）         │
 └────────────────────────────────────────────────┘
      │
      ▼
 ┌─────────── Policy（approval/policy.go）─────────┐
 │ 有没有规则授权「这些告警 + 这个动作」？               │
 │ Action.Prepare：读实时对象，冻结执行需要的一切        │
 │ 拒绝：急停 / 服务忙 / 预算用完 / 前提不满足           │
 │ 降级：auto → manual（维护窗口 / 被阻断 / 已执行过 /   │
 │       监控缺失）                                   │
 │ 通过 → ExecutionContext 快照 + plan_hash           │
 └────────────────────────────────────────────────┘
      │ observe：只记录「规则本来会做什么」
      │ manual：审批单 pending，等人在飞书卡片或 Web 上批准（带 plan_hash）
      │ auto：审批单直接 approved（批准人是规则本身）
      ▼
 执行器（亮点四）：认领时在锁内把以上条件全部重查一遍
```

## 面试怎么讲

**30 秒版本：**
我们的原则是：模型只能提议，执行权在代码。模型输出的建议要过两道确定性闸门。第一道 Guard 只看结构化事实，比如重启的目标必须是 docker inspect 确认过 ID 的容器，容器确实停了，数据库和 Redis 正常；不满足就把建议改成不做。第二道 Policy 看处置规则：规则授权的是「这类告警 + 这个动作」，分 observe、manual、auto 三档，auto 在维护窗口、监控缺失等情况下自动降为人工。通过后，把目标 ID、执行前状态、验证标准冻结成快照，算出 plan_hash。人批准时要带上这个 hash，执行器认领时还会在锁内再核对一遍。

**常见追问：**

- **模型说置信度 high、风险 low，为什么还要人批准？** 模型的自我评估没有经过校准，不能当证据。执行许可只来自事先审核过的规则，一条新规则应该先用 observe 模式试运行。
- **Guard 的规则会不会太死板？** 会，而且这是有意的：Guard 宁可拦下一个本来正确的动作（转人工），也不放过一个错误的动作。它只负责判断前提是否成立，不负责替人做决定。
- **规则改了，之前批准的审批单还有效吗？** 无效。规则版本由「人工标签 + 规则、服务、验证配置的内容摘要」组成，写进快照。配置一改，版本就变，旧快照在认领时直接失效，包括正在进行中的验证。
- **plan_hash 防的是什么？** 防的是「批准的内容」和「执行的内容」不一致：数据库里的审批单被篡改、前端展示的是旧版本、卡片按钮被伪造，都会因为 hash 对不上而被拒绝。
