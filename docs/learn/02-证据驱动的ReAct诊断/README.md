# 亮点二：证据驱动的 ReAct 诊断

> 返回：[知识库首页](../README.md)

## 一句话（简历写法）

基于 Eino ReAct 构建证据驱动的故障诊断链路：由代码预先采集 11 类证据并区分「缺席 / 观测失败 / 故障」，模型只能调用只读工具补查；结合步数、上下文、时间三重预算和结构化输出契约，把大模型的推理约束为可审计、可回放的一段 JSON 建议。

## 它解决什么问题

- 让模型自己决定查什么，它会漏查、乱查，还会编造指标名和容器名。
- 日志、告警描述都是外部文本，里面的一句话可能被模型当成指令（提示词注入）。
- 模型可能一直查下去不给结论，上下文越积越长，最终超限。
- 模型的输出格式不稳定，下游无法可靠解析。

## 方案全景

```text
Pipeline.Run（每个 agent_run 一次）
  1 记忆查找（亮点五）
  2 证据采集：11 个采集器按固定顺序执行 → Evidence
       → 渲染成文本（声明「不可信数据」、结构化事实单独成行）
       → 先存回放快照
  3 推理：Eino ReAct 循环
       系统提示词（动作清单由已启用的动作自动生成）
       + 证据文本
       + 5 个只读工具（查 Prometheus、看 Docker）
       ── 步数上限 / 最后一轮禁止调工具 / 上下文预算 / 3 分钟超时
       → 输出 JSON：{rca, confidence, evidence_refs, plan}
       → 按契约校验，不合格带着原文重试 1 次
  4 Guard  5 Policy  6 通知（亮点三）
```

## 面试怎么讲

**30 秒版本：**
诊断链路我们的原则是「证据先行、模型只读」。代码先从 11 个数据源采证据，每项都标明是正常、部分失败、未配置还是采集失败，关键事实单独存成结构化字段。模型在 Eino 的 ReAct 循环里读证据，只能调用 5 个只读工具补查，写操作根本不在它的工具列表里。我们给它设了步数、上下文、时间三重预算，最后一轮强制它给结论。输出必须是固定格式的 JSON，动作名只能从已启用的动作里选；提示词里的动作清单和解析器的白名单来自同一份定义。整个输入在调用模型前就存进回放快照，事后能原样复现。

**常见追问：**

- **为什么不让模型自己决定查什么？** 这个服务该看哪些数据源是确定的，代码能保证每次都查全、查法一致、结果可复现。模型只负责「看完之后还缺什么再补」。这也和成本有关：固定证据是 0 次模型调用。
- **模型给的结论错了怎么办？** 模型的输出只是建议。能不能执行由后面的 Guard（查事实前提）和 Policy（查规则授权）决定，执行后还有独立验证。诊断错了，最坏结果是一个被拒绝的建议。
- **上下文超了怎么办？** 超过额度 80% 时，只压缩较早的工具结果（Prometheus 曲线只保留首尾和极值）；原始证据和最近一批工具结果不动。压缩后仍然超限就报错，不会悄悄丢掉证据。
- **Eino 在这里做了什么，你们自己做了什么？** Eino 负责 ReAct 循环本身：调模型、执行工具、把结果拼回消息历史。我们在外面包了一层模型（控制最后一轮、做上下文预算、统计 token）和一层工具适配器（参数规范化、统一超时、脱敏、截断、记录审计），流水线编排、校验和审批都在 Eino 之外。
