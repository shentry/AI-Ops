# 预算控制：步数、上下文与超时

> 所属：[亮点二 · 证据驱动的 ReAct 诊断](README.md)

## 一句话

ReAct 循环必须有上限，否则模型可能一直查下去。本项目有三重预算：**步数**（最后一轮强制给结论）、**上下文**（超过 80% 时压缩较早的工具结果，证据不动）、**时间**（整次诊断 3 分钟）。

## 先弄懂：为什么需要预算

- **Token**：模型按 token 处理文字。一个汉字大约是 1～2 个 token，具体取决于模型的分词器。输入和输出都按 token 计费。
- **上下文窗口**：模型一次最多能读多少 token。超过就报错。
- ReAct 循环里，每调一次工具，工具结果都会追加进消息历史，**上下文只增不减**。

没有预算会出现三种问题：

1. **不收敛**：模型一直「再查一个指标看看」，永远不给结论。
2. **超限**：工具结果越积越多，最终超过上下文窗口，请求直接失败。
3. **上下文腐化**：窗口还装得下，但信息太多，模型反而找不到关键内容。

## 第一重：步数预算

步数上限按诊断模式取（`config.example.yaml`）：

```yaml
diagnose:
  budget:
    full_steps: 32   # critical、high 级别
    light_steps: 16  # warning 级别，以及未知模式
```

Eino 的循环里，**模型调用一次算一步，执行一批工具算一步**。步数用完时，Eino 直接返回 `ErrExceedMaxSteps` 错误（`compose/graph_run.go`），前面的推理全部白费。所以本项目在模型外面包了一层，**提前一轮强制收尾**：

```go
// 摘自 internal/llm/diagnosis_model.go（有删减）
func (m *diagnosisModel) Generate(ctx context.Context, input []*schema.Message, opts ...model.Option) (*schema.Message, error) {
	toolRounds := 0 // 数一数已经调过几轮工具
	for _, msg := range input {
		if msg != nil && msg.Role == schema.Assistant && len(msg.ToolCalls) > 0 {
			toolRounds++
		}
	}
	// 已用 2×toolRounds 步，本次模型调用是下一步。
	// 如果这次还调工具（+1 步），就没有步数留给最终回答（再 +1 步），所以这一轮必须直接回答
	finalTurn := 2*toolRounds+3 > m.maxSteps
	if finalTurn {
		opts = append(opts, model.WithToolChoice(schema.ToolChoiceForbidden)) // 禁止调工具
		input = append(input, schema.UserMessage(
			"取证预算已结束。根据已有证据输出简短的最终 JSON；缺失信息写入 rca，不再调用工具。目标或动作不确定时 plan.action=none。"))
	}
	input, err := m.context.prepare(input) // 第二重预算：上下文
	if err != nil {
		return nil, err
	}
	msg, err := m.ToolCallingChatModel.Generate(ctx, input, opts...)
	m.context.observe(msg) // 用真实 token 用量校准估算器
	if err == nil && finalTurn && msg != nil && len(msg.ToolCalls) > 0 {
		return nil, errors.New("llm: model requested tools after evidence budget ended")
	}
	return msg, err
}
```

最后一轮做了三件事：

1. 通过接口参数禁止调用工具；
2. 追加一句话告诉模型「预算结束，缺什么写进 rca」；
3. 模型仍然要求调工具，就直接报错。

提示词里还有一条配套纪律：「只有工具能回答影响结论的具体问题时才补查……不反复扩大查询范围。」

## 第二重：上下文预算

每次调用模型前，先估算这次输入有多少 token（消息 + 工具定义），和模型的输入额度比较：

```go
// 摘自 internal/llm/context_budget.go 的 prepare（有删减）
func (b *contextBudget) prepare(messages []*schema.Message) ([]*schema.Message, error) {
	size := estimate(messages) + b.toolTokens
	out := messages
	if size > b.inputLimit - b.inputLimit/5 { // 超过额度的 80% 才开始压缩
		lastBatch := /* 最近一批工具调用在消息里的位置 */
		out = append([]*schema.Message(nil), messages...) // 在副本上改，不动 Eino 的原始历史和审计
		for i := 0; i < lastBatch && size > b.inputLimit-b.inputLimit/5; i++ {
			msg := messages[i]
			if msg == nil || msg.Role != schema.Tool {
				continue // 只动工具结果；系统提示词、证据、模型自己的消息都不动
			}
			content := compactToolResult(msg.ToolName, msg.Content)
			if content != msg.Content {
				copy := *msg
				copy.Content = content // 保留调用 ID 等协议字段，只换内容
				out[i] = &copy
				size = /* 重新估算 */
			}
		}
	}
	if size > b.inputLimit {
		// 压缩后仍然放不下：报错，不悄悄删证据，也不发出一个明知会超限的请求
		return nil, fmt.Errorf("%w: estimated input %d > %d", ErrContextBudget, size, b.inputLimit)
	}
	return out, nil
}
```

**保护什么、压缩什么：**

| 内容 | 处理 |
|---|---|
| 系统提示词 | 不动 |
| 原始证据（第一条 user 消息） | 不动：它是 Guard 复核的依据，压缩后模型的结论可能建立在它没看到的信息上 |
| 模型自己的消息（包括思考内容、工具调用请求） | 不动 |
| 最近一批工具结果 | 不动：模型下一步马上要用 |
| **更早的工具结果** | **可以压缩**：模型已经看过，并基于它做了后续推理 |

**怎么压缩？** 目前只压缩格式确定的 `prom_range_query` 结果：保留完整的结构和每条序列的标签，只把采样点数组换成「首点、末点、最小值、最大值 + 原始点数」，并明确标注「中间采样点已省略」（不是「没有异常」）。格式未知、已经截断、含 NaN 的结果一律原样保留，**不猜哪些信息可以丢**。

**估算准不准？** 不追求精确。模型网关没有提供分词器，所以用启发式估算：

```go
// 摘自 internal/llm/token_estimator.go（有删减）
// ASCII（英文、代码）按 3 个字符算 1 个 token，非 ASCII（中文等）按 2 个 UTF-8 字节算 1 个 token
func estimatedTextTokens(text string) int {
	ascii, nonASCII := 0, 0
	for _, r := range text {
		if r < utf8.RuneSelf {
			ascii++
		} else {
			nonASCII += utf8.RuneLen(r)
		}
	}
	return (ascii+2)/3 + (nonASCII+1)/2
}

// 估算值再乘一个系数，系数至少 1.2（留 20% 余量）
func (e *tokenEstimator) estimate(raw int) int { return int(math.Ceil(float64(raw) * e.scale())) }

// 每次模型返回真实的 PromptTokens 后校准：取「历史最大低估比例 × 1.1」，
// 这样一次很短的请求不会把从密集文本里学到的余量抹掉
func (e *tokenEstimator) observe(raw, promptTokens int) {
	e.factor = math.Max(e.scale(), float64(promptTokens)/float64(raw)*1.1)
}
```

系数只会变大、不会变小，宁可早一点压缩，也不要发出一个超限的请求。统计信息（压缩次数、估算值、实际值、节省量）会写进诊断步骤的审计里。

## 第三重：时间预算

```go
ctx, cancel := context.WithTimeout(ctx, 3*time.Minute) // Reasoner.Diagnose 开头
```

**为什么是 3 分钟？** 诊断 worker 把超过 5 分钟还在 running 的任务视为「进程死了」，放回队列重新执行。诊断必须在 5 分钟内结束，否则同一个任务可能被执行两次。3 分钟留出了余量，包括解析失败后的那一次重试。

## 预算用完之后

| 情况 | 结果 |
|---|---|
| 到最后一轮 | 强制输出结论，缺什么写进 rca，不确定就 `action: none` |
| 上下文压缩后仍超限 | 本次诊断失败，记录原因 |
| 超时 | 本次诊断失败，打开待处理问题 `reasoner_timeout` |

失败的诊断不会产生任何动作建议。值班人员能在控制台看到失败原因，可以手动重新诊断。

## 常见追问

- **80% 这个阈值怎么来的？** 预留余量：估算有误差，模型输出也要占空间。这是经验值，配合真实 token 用量校准。
- **为什么不在上下文快满时，让模型自己总结一下？** 让模型总结会多一次调用，而且摘要可能丢掉关键事实。这里的压缩是确定性的，只作用于格式已知的旧结果，行为可预测、可测试。
- **full 模式为什么是 32 步？** 配置注释写得很明白：步数「只作异常兜底」。正常诊断几步就结束，32 步是防止失控的上限，不是期望值。
