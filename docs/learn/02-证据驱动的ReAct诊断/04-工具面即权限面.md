# 工具面即权限面

> 所属：[亮点二 · 证据驱动的 ReAct 诊断](README.md)

## 一句话

模型能调用的工具，就是它的全部权限。本项目只给模型 5 个只读工具；写操作是另一类对象（Action），根本不在模型的工具列表里，模型编造动作名也调不到。所有工具调用都经过同一个入口，统一处理超时、脱敏和截断。

## 先弄懂：大模型怎么「调用工具」

模型本身不能执行任何代码，它只能**输出一段文字**，说明「我想调用某个工具，参数是什么」（function calling）。真正执行工具的是框架代码。所以：

- 工具列表里没有的能力，模型永远用不了。
- 工具怎么执行、能访问什么，完全由代码决定。

这就是「工具面即权限面」：**想限制模型能做什么，就限制给它的工具。**

## 两类对象：只读工具 vs 写动作

```go
// 摘自 internal/tools/registry.go（有删减）
// Registry 是进程内唯一的工具目录：只读工具 + 写动作。
// 注册在启动时完成，运行时只读，所以不需要锁
type Registry struct {
	tools   map[string]ToolSpec // 只读工具：模型、证据采集、恢复验证都可以用
	actions map[string]Action   // 写动作：只有执行器能按批准过的快照调用
}

// ForLLM 导出全部只读工具：模型看到的工具面就是它的全部权限面。
// 写动作不在这里，模型编造动作名也调不到；它只能在计划里建议已启用的动作
func (r *Registry) ForLLM() []ToolSpec {
	exposed := make([]ToolSpec, 0, len(r.tools))
	for _, spec := range r.tools {
		exposed = append(exposed, spec)
	}
	// 按名字排序：每次导出顺序一致，提示词里的工具清单稳定，可以比对
	sort.Slice(exposed, func(i, j int) bool { return exposed[i].Name < exposed[j].Name })
	return exposed
}
```

注册时会做校验：名字、描述、处理函数、超时缺一个就启动失败；只读工具和写动作不能重名。问题在启动时就暴露，而不是等模型真正调用时才出错。

## 模型能用的 5 个只读工具

| 工具 | 参数 | 作用 |
|---|---|---|
| `prom_series_meta` | `match`（序列选择器）、`limit` | 查有哪些指标和标签。提示词要求**先调它，再写 PromQL**，不许凭空编造指标名 |
| `prom_instant_query` | `query`、`time` | 查某一时刻的值 |
| `prom_range_query` | `query`、`start`、`end` | 查一段时间的曲线，时间范围有上限（默认 15 分钟） |
| `docker_inspect` | `name` | 查看容器状态：ID、镜像、状态、重启策略、重启次数、时间戳 |
| `docker_logs` | `name`、`tail`、`since` | 读日志，按模式聚合后返回（每类日志的次数、首末时间、最新样例），不会持续跟随 |

Docker socket 不可用时，只注册前 3 个。Docker 工具可以按名字查看宿主机上的任意容器，但只能看，不能改。

## 统一执行入口：超时、脱敏、截断

```go
// 摘自 internal/tools/registry.go（有删减）
// 只读工具的唯一执行入口。模型的工具循环、证据采集、恢复验证都走这里，
// 所以这三条纪律只有一份实现；模型看到的输出和存进审计的内容，是同一份脱敏后的文本
func (r *Registry) ExecuteWithMetadata(ctx context.Context, name string, args json.RawMessage) (string, ExecutionMetadata, error) {
	spec, ok := r.tools[name]
	if !ok {
		return "", ExecutionMetadata{}, ErrToolNotRegistered // 不在名单里一律拒绝，没有默认放行
	}
	ctx, cancel := context.WithTimeout(ctx, spec.Timeout) // 1. 超时
	defer cancel()
	output, err := spec.Handler(ctx, args)
	if err != nil {
		return "", ExecutionMetadata{}, fmt.Errorf("tools: %s failed: %w", name, err)
	}
	clean := Sanitize(ToSafeText(output))                // 2. 脱敏、去控制字符
	truncated := Truncate(clean, spec.MaxOutput)         // 3. 截断（默认 4096 个字符）
	return truncated, ExecutionMetadata{Truncated: truncated != clean}, nil
}
```

被截断的输出末尾会加上 `…[truncated]` 标记，同时通过 `Truncated` 元数据告诉调用方。**让模型知道它看到的不是全部**，否则它可能以为「没看到异常」就等于「没有异常」。

## 工具报错：当成观测结果喂回去，不中断循环

```go
// 摘自 internal/llm/reasoner.go（有删减）
// 把注册表里的只读工具适配成 Eino 的工具接口
func (t *registryTool) InvokableRun(ctx context.Context, argumentsInJSON string, _ ...tool.Option) (string, error) {
	started := time.Now().UTC()
	output, metadata, err := executeLLMTool(ctx, t.registry, t.spec.Name, argumentsInJSON)
	entry := StepLog{Name: t.spec.Name, Input: argumentsInJSON, Truncated: metadata.Truncated, StartedAt: started, FinishedAt: time.Now().UTC()}
	if err != nil {
		// Prometheus 抖一下，不应该让整次诊断失败。
		// 模型看到失败后，可以基于其余证据给出低置信度的结论
		entry.Err = tools.Sanitize(err.Error())
		t.recorder.record(entry) // 审计里仍然记下错误
		return "tool error: " + entry.Err, nil
	}
	entry.Output = output
	t.recorder.record(entry)
	return output, nil
}
```

每次工具调用都记录成一条审计步骤（输入、输出、耗时、是否截断、错误）。同一个工具用完全相同的参数被调用到第 3 次时，打开一个待处理问题 `tool_repeated`，提示模型可能在原地打转。

## 参数保真：网关会篡改工具参数

一些 OpenAI 兼容的模型网关有个坑：流式输出工具参数时，会把一个空对象占位和真实参数拼在一起，工具收到的变成：

```text
{}{"query":"up{job=\"sub2api\"}"}
```

这不是合法 JSON，工具会直接报错。模型没有做错，是传输层改了参数。

```go
// 摘自 internal/llm/tool_args.go（有删减）
// 只做两种安全的折叠：丢掉空对象占位、合并完全相同的重复值。
// 出现两个不同的非空值时拒绝执行（fail closed），不猜哪个才是模型本意
func normalizeToolArguments(raw string) (string, error) {
	decoder := json.NewDecoder(strings.NewReader(strings.TrimSpace(raw)))
	var first json.RawMessage
	decoder.Decode(&first)
	selected := first
	// ……逐个读出后续 JSON 值：空对象跳过；与已选值相同则跳过；不同则报错……
	if !repeated {
		return raw, nil // 只有一个 JSON 值：保留原始字节，审计里就是模型原本的输出
	}
	return string(bytes.TrimSpace(selected)), nil
}
```

这里的思路是：**先核对「模型请求的」和「工具实际收到的」是否一致；是传输层的问题，就修传输层，不要怪模型。**

## 常见追问

- **为什么不干脆给模型一个「执行 shell」的通用工具？** 通用执行器很灵活，但权限边界难以控制。本项目的写操作涉及生产，每个动作都需要精细的前提检查、身份核对、结果对账，这些只有专用动作才能做到。
- **工具太多了怎么办？** 本项目只有 5 个，全部直接交给模型就行。工具多到几十上百个时，才需要先给索引、再按需加载定义（渐进式披露）。
- **为什么所有参数都按字符串传？** 实现简单：Handler 自己负责解析和校验。模型对字符串参数的遵循度也比较高。
