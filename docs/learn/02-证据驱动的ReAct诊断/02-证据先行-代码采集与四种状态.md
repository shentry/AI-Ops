# 证据先行：代码采集与四种状态

> 所属：[亮点二 · 证据驱动的 ReAct 诊断](README.md)

## 一句话

模型开始推理之前，代码已经从 11 个数据源把证据采齐了。每项证据都标明四种状态之一：正常、部分失败、未配置、采集失败；关键事实另存为结构化字段，供后面的 Guard 使用。

## 为什么不让模型从零开始查

| 如果让模型自己决定查什么 | 由代码先采 |
|---|---|
| 可能漏查关键数据源（比如忘了看数据库） | 该看的数据源每次都查 |
| 每次查法不同，结果无法对比、无法复现 | 顺序和查询语句固定，同样的输入渲染出同样的文本 |
| 每查一次都要消耗一轮模型调用 | 固定证据不消耗模型调用 |
| 查询语句由模型编写，可能拼出危险的查询 | 查询模板写死在代码里，不接受外部输入拼接 |

模型的角色变成：**看完这些证据，还缺什么，再用只读工具补查。**

## 11 个采集器

按固定顺序执行（顺序在 `cmd/server/main.go` 里写死）：

| 证据名 | 数据源 | 采什么 |
|---|---|---|
| `alert_snapshot` | 数据库 | incident 成员列表、每条当前告警的 labels 和 annotations。这是「发生了什么」的第一手材料 |
| `prom_replay` | Prometheus | 回放告警本身的 PromQL 表达式，取告警时刻前后的曲线 |
| `golden_metrics` | Prometheus | 宿主机黄金指标：CPU、内存、磁盘、网络。PromQL 模板写死在代码里 |
| `sub2api_health` | HTTP `/health` | 进程是否在响应。sub2api 的 `/health` 不检查依赖，**只能证明进程活着，不能证明业务可用** |
| `sub2api_metrics` | Prometheus（由 sub2api-exporter 导出） | 真实流量：请求数、错误数、错误率，同时给出告警前的基线值和当前值 |
| `upstream_accounts` | sub2api 管理接口（只读） | 上游账号的调度状态，以及最近 5 分钟每个账号的错误数 |
| `recent_changes` | 数据库（发布记录表） | 告警前 60 分钟内的发布、可以回退到的历史版本 |
| `postgres` | PostgreSQL（只读账号） | 连通性、连接数、等待中的会话数。查询是固定的只读语句 |
| `redis` | Redis | PING 延迟、内存占用、连接数。只用 PING 和 INFO 两个命令 |
| `docker_inspect` | Docker Engine API | 容器身份（ID）和状态：是否在运行、退出码、是否 OOM、重启次数、重启策略 |
| `docker_logs` | Docker Engine API | 最近的容器日志，按模式聚合（每类日志出现几次、首末时间、最新一条样例） |

## 采集器的约定：不返回错误

```go
// 摘自 internal/diagnose/evidence.go
// 约定：Collect 不返回 error。失败时把 EvidenceItem.Status 置为 error 并填写 Err，
// 这样单个采集器失败不会阻断其他证据的采集
type Collector interface {
	Name() string
	Collect(ctx context.Context, target Target) EvidenceItem
}

// 依次执行所有采集器；每个采集器自己控制超时（默认 5 秒）
func BuildEvidence(ctx context.Context, collectors []Collector, target Target) Evidence {
	evidence := Evidence{IncidentID: target.Incident.ID, Items: make([]EvidenceItem, 0, len(collectors))}
	for _, collector := range collectors {
		evidence.Items = append(evidence.Items, collector.Collect(ctx, target))
	}
	return evidence
}
```

Prometheus 挂了，Docker 证据照样能采到；Redis 没配置，其他证据不受影响。

## 证据的数据结构

```go
// 摘自 internal/diagnose/evidence.go（有删减）
type EvidenceItem struct {
	Name        string    // 证据名，比如 docker_inspect
	Source      string    // 数据源，比如 docker:inspect
	CollectedAt time.Time
	Status      string    // ok / partial / missing / error

	// —— 结构化事实：Guard 只信这些字段，不解析 Body ——
	Object    *ObjectRef       // 这项证据描述的对象（容器、服务、上游账号），带可信 ID
	Container *ContainerFacts  // 容器是否在运行、是否在重启、OOM、退出码、重启策略……
	Health    *HealthFacts     // healthy / unhealthy / unavailable + 状态码 + 延迟
	Release   *ReleaseFacts    // 当前发布 ID、是否在故障前不久发布……
	Upstream  *UpstreamFacts   // 每个上游账号的错误数、是否可调度……
	Business  *tools.BusinessTraffic // 请求数、错误数

	Body      string // 给模型看的正文：脱敏后截断到 2048 个字符
	Truncated bool
	Err       string
}
```

两类信息分开存放，是整个诊断设计的关键：

- **Body（正文）**：给模型读的文字，可以截断，可以不完整。
- **结构化事实**：给代码判断用的字段，不会被截断，只来自可信的数据源。比如 `Object.ID` 只能来自 Docker 的响应，不能来自告警标签或日志文本。

## 四种状态：缺席、观测失败、故障必须分开

```go
const (
	ItemOK      = "ok"      // 采到了
	ItemPartial = "partial" // 多项查询中有部分失败，正文逐项记录
	ItemMissing = "missing" // 数据源没有配置：属于部署形态，不是故障
	ItemError   = "error"   // 配置了但采集失败，或者读到了数据源本身不健康
)
```

有四个辅助函数统一处理「收尾」：

| 函数 | 场景 | 结果 |
|---|---|---|
| `finishItem` | 正常采集 | ok；正文脱敏、去控制字符、截断。出错时 error，丢弃正文 |
| `degradedItem` | 采到了，但数据源本身不健康（比如 `/health` 返回 500） | error，**保留正文**，因为这个 500 响应体正是诊断需要看的 |
| `queriesItem` | 一个采集器发了多条查询（比如黄金指标） | 全部成功为 ok，全部失败为 error，部分失败为 partial |
| `missingItem` | 没配置这个数据源 | missing |

**为什么要分这么细？** 同样是「error」，可能有两种完全不同的含义：

- 读到了 HTTP 500：这是**故障证据**。
- 连接超时：这是**观测失败**，服务本身未必有问题。

两者靠结构化事实区分：`Health.Observation` 前者是 `unhealthy`，后者是 `unavailable`。**观测失败既不等于健康，也不等于故障。** 这一点贯穿整个项目：

- 系统提示词告诉模型：「status 为 error/partial/missing 表示观测不完整，不等于服务健康或已确认故障」。
- Policy 在监控数据缺失时，会把自动执行降级为人工（见亮点三）。
- 恢复验证时，拿不到数据记为 unavailable，不算健康（见亮点五）。

## 采集之后：先存快照，再交给模型

```go
// 摘自 internal/diagnose/pipeline.go 的 Run（有删减）
collected, err := p.builder.BuildForIncident(ctx, run.IncidentID)
rendered := collected.Render() // 渲染成给模型看的文本（见下一篇）

// 回放记录先存结构化证据。关键证据存不下，就不发布任何计划
evidenceJSON, _ := json.Marshal(collected)
snapshot := store.DiagnosisSnapshot{RunID: run.ID, CodeVersion: codeVersion, EvidenceJSON: evidenceJSON /* … */}
if err := p.db.SaveDiagnosisSnapshot(ctx, snapshot); err != nil {
	return p.fail(ctx, run, err)
}
```

同时，每项证据的采集结果会变成一条事件（`collector.completed` 或 `collector.failed`）。采集失败的证据项会打开一个待处理问题 `collector_failed_<证据名>`，下次采集成功时自动关闭。值班人员在控制台能直接看到「这次诊断缺了哪项数据」。

## 两种额外注入的上下文

证据文本前面，有时会多出一段：

- **重新诊断时**：注入上一轮的根因、计划和验证失败的详情，并明确写着「上一轮动作的恢复验证失败，不要复用计划，仅供对照」。
- **故障记忆未命中、但同类故障执行过动作时**：注入最近 5 条历史执行记录，标题写明「仅供参考，不构成权限依据」。

## 常见追问

- **采集器都串行执行，不慢吗？** 每个数据源客户端都有自己的超时（证据采集默认 `evidence.timeout_seconds: 5`），单个数据源卡住不会无限拖延。和模型推理（秒级到分钟级）相比，这点时间可以接受，而且串行换来了稳定的顺序。
- **为什么查询模板要写死？** 采集器的 PromQL、SQL、Redis 命令都不接受外部输入拼接。告警标签来自外部，拼进查询语句就有注入风险。模型想查别的，只能通过只读工具，而工具有自己的超时和输出上限。
