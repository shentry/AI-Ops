# 告警的三层身份：指纹、内容哈希、分组键

> 所属：[亮点一 · 告警摄入与 Incident 归并](README.md)

## 一句话

每条告警算三个身份：

- **指纹（Fingerprint）**：它是哪个告警对象？
- **内容哈希（AlertHash）**：和上次相比，内容有没有变？
- **分组键（GroupKey）**：它属于哪个故障？

去重靠前两个，归并靠第三个。

## 先弄懂：labels 就是告警的身份证

Prometheus 里，一条告警由它的 labels 唯一确定。比如：

```text
alertname=Sub2APIDown, service=sub2api, instance=node-a, severity=critical
```

labels 相同，就是同一条告警在不同时刻的推送；labels 不同（比如 `instance=node-b`），就是另一条告警。`annotations`（描述文字）不参与身份判断。

解析报文时，所有 label 的 key 都会转成小写，这样 `AlertName` 和 `alertname` 会被当成同一个 key。

## 第一层：指纹，回答「它是谁」

```go
// 摘自 internal/ingest/fingerprint.go
// 指纹 = 选中 labels 的 SHA-256。不包含 status，所以 firing 和 resolved 共用同一个指纹。
func Fingerprint(labels map[string]string, fields []string) string {
	keys := fingerprintKeys(labels, fields) // fields 为空时取全部 labels，然后按 key 排序
	var input strings.Builder
	for _, key := range keys {
		input.WriteString(key)
		input.WriteByte('=')
		input.WriteString(labels[key])
		input.WriteByte(0) // 每一对以 NUL 结尾
	}
	digest := sha256.Sum256([]byte(input.String()))
	return hex.EncodeToString(digest[:])
}
```

逐行理解：

- **key 要排序**：Go 的 map 遍历顺序是随机的，不排序的话，同一组 labels 每次算出来的指纹都可能不同。
- **用 `=` 和 NUL 分隔**：避免拼接歧义。如果直接拼接，`{a: "bc"}` 和 `{ab: "c"}` 都会变成 `abc`；加上分隔符后分别是 `a=bc\0` 和 `ab=c\0`。
- **不包含 status**：同一条告警 firing 时和 resolved 时的指纹相同，这样恢复消息才能找到它对应的那条记录。
- **可配置取哪些 labels**：`ingest.fingerprint_fields` 为空（默认）时用全部 labels。如果配置了字段，而某条告警一个都没有，就拒收这条报文。否则它会对空串算哈希，所有这类告警会被当成同一个对象。

## 第二层：内容哈希，回答「变没变」

```go
// 摘自 internal/ingest/fingerprint.go（有删减）
// 参与哈希的字段：来源、名称、状态、级别、labels、annotations、generatorURL、指纹。
// 不参与的字段：StartsAt、EndsAt、ReceivedAt（时间字段）。
func FullHash(a NormalizedAlert) string {
	payload := struct{ /* 上面列出的字段 */ }{ /* … */ }
	encoded, _ := json.Marshal(payload) // Go 的 json 对 map 按 key 排序，结果是稳定的
	digest := md5.Sum(encoded)
	return hex.EncodeToString(digest[:])
}
```

**为什么不含时间字段？** Alertmanager 重复推送时，内容不变，但接收时间每次都不同。如果把时间算进去，每次重复推送都会被当成「变化」。

**为什么含 status 和 severity？** firing 变 resolved、warning 升 critical，都是需要处理的真实变化。

## 去重：三种结论

指纹和内容哈希组合起来，每条新告警和该指纹的最新状态（`last_alert` 表）对比，得出三种结论：

| 结论 | 条件 | 写库动作 | 后续 |
|---|---|---|---|
| **New**（新告警） | 这个指纹第一次出现 | 插入 `alert` 一行、`last_alert` 一行，`firing_count = 1` | 交给归并器 |
| **Full**（完全重复） | 指纹相同，内容哈希相同 | **不插入** alert 行，只更新 `last_alert.last_seen` | 给所属 incident 续心跳 |
| **Partial**（内容变化） | 指纹相同，内容哈希不同 | 插入一行新版本的 alert，`last_alert` 指向它，`firing_count + 1` | 交给归并器 |

```go
// 摘自 internal/store/rawevent.go 的 applyAlert（有删减）
var last LastAlert
// FOR UPDATE：同一指纹并发到达时，后到的事务等先到的提交，
// 不会两边都读到「不存在」然后各插一份
err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).
	Where("fingerprint = ?", input.Fingerprint).First(&last).Error

if errors.Is(err, gorm.ErrRecordNotFound) {
	tx.Create(&alert)
	tx.Create(&LastAlert{Fingerprint: input.Fingerprint, AlertID: alert.ID, AlertHash: input.AlertHash, FiringCount: 1 /* … */})
	return AlertApplyResult{Dedup: DedupNew /* … */}, nil
}
if last.AlertHash == input.AlertHash {
	// 完全重复：不插 alert 行，告警持续期间 alert 表不会膨胀
	tx.Model(&LastAlert{}).Where("fingerprint = ?", input.Fingerprint).Update("last_seen", input.ReceivedAt)
	return AlertApplyResult{Dedup: DedupFull /* … */}, nil
}
// 内容变化：追加新版本
tx.Create(&alert)
tx.Model(&LastAlert{}).Where("fingerprint = ?", input.Fingerprint).Updates(map[string]any{
	"alert_id": alert.ID, "alert_hash": input.AlertHash, "status": input.Status,
	"firing_count": gorm.Expr("firing_count + ?", 1), // 在 SQL 里原子自增，而不是读出来加 1 再写回
	// …
})
return AlertApplyResult{Dedup: DedupPartial /* … */}, nil
```

两个细节：

- `firing_count` 用 `firing_count + 1` 在 SQL 里自增，并发下不会丢计数。
- 内容变化时，如果这个告警已经挂在某个 incident 上，会先锁住那个 incident，因为告警变化也会改变故障的范围。

**举个例子**（同一个 `Sub2APIDown`）：

| 时间 | 推送内容 | 结论 |
|---|---|---|
| 10:00 | firing, severity=warning | New |
| 10:04 | 原样重复推送 | Full：只续心跳 |
| 10:06 | severity 变成 critical | Partial：新版本 |
| 10:20 | status=resolved | Partial：状态变化，会触发关单判断 |

## 第三层：分组键，回答「属于哪个故障」

```go
// 摘自 internal/ingest/correlate.go
// 按配置的 group_by 取 label 值拼成分组键。
// 缺少配置的 label 时回退成 "name:"+告警名，避免不相干的告警被并进同一个「空分组」。
func GroupKey(alert CorrelationInput, cfg config.CorrelateConfig) string {
	values := make([]string, 0, len(cfg.GroupBy))
	for _, field := range cfg.GroupBy {
		field = strings.TrimPrefix(strings.TrimSpace(field), "labels.")
		value, ok := alert.Labels[field]
		if !ok || strings.TrimSpace(value) == "" {
			return "name:" + alert.Name
		}
		values = append(values, value)
	}
	if len(values) == 0 {
		return "name:" + alert.Name
	}
	return strings.Join(values, ",")
}
```

默认配置是 `group_by: [labels.service]`。所以 sub2api 的 Down、错误率、延迟告警，分组键都是 `sub2api`，会归进同一个 incident。分组键超过 255 个字符的 firing 告警会被拒收（数据库字段宽度就是 255）。

## 附：告警级别

级别从 `severity` label 映射成 1 到 5 的数字，之后决定诊断力度（见[下一篇](04-Incident归并与生命周期.md)）：

| label 值 | 数值 |
|---|---|
| critical | 5 |
| error / high | 4 |
| warning / medium | 3 |
| info | 2 |
| low | 1 |
| 缺失或未知 | **3（warning）** |

缺失时默认 warning 而不是 info，因为 info 在默认配置里会跳过诊断。一条标签写错的告警，宁可多诊断一次，也不要漏掉。

## 常见追问

- **为什么指纹不能包含 status？** 包含的话，resolved 消息算出的指纹和 firing 时不一样，就找不到原来的告警，incident 永远关不了单。
- **完全重复为什么还要更新 `last_seen`？** incident 的时间窗靠最近一次活跃时间续命。告警一直在响，incident 就应该一直开着；不续的话，15 分钟后同一次故障会被当成一个新 incident。
- **内容哈希为什么用 MD5？** 它只用来比较「内容变没变」，不承担安全职责，也没有人会故意构造碰撞。指纹是长期保存、对外可见的对象身份，用的是 SHA-256。
