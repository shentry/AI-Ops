# 亮点一：告警摄入与 Incident 归并

> 返回：[知识库首页](../README.md)

## 一句话（简历写法）

设计基于 MySQL 的告警持久化摄入链路：Webhook 先落库再返回，后台单消费者按顺序处理；用「对象指纹 + 内容哈希」两级去重、「分组键 + 时间窗」归并，把告警风暴收敛成少量 Incident。归并和诊断排队在同一个事务里完成，进程崩溃也不丢告警。

## 它解决什么问题

- **告警会重复推。** 故障持续期间，Alertmanager 会反复推同一条告警。
- **一个故障会触发多条告警。** 服务挂了，Down、错误率、延迟告警会一起响。
- **处理慢，进程会崩。** 诊断要调大模型，耗时以分钟计。Webhook 不能干等，事件也不能丢。

## 方案全景

```text
Alertmanager ──POST──▶ Webhook handler ──写入──▶ raw_event(pending) ──▶ 返回 202
                             │ Notify（只是唤醒信号）
                             ▼
                  ingest.Worker（单个 goroutine，按 id 顺序消费）
                    解析报文 → 计算三层身份 → 开启一个事务 {
                        去重：对比 last_alert（新告警 / 完全重复 / 内容变化）
                        归并：找到或新建 incident，挂上成员
                        incident 升级为 firing 的那一刻：排队一条诊断任务 agent_run
                        raw_event 标为 processed
                    }
```

## 读完本亮点你会知道

- 为什么入口只「收下并存好」，处理放到后台；为什么 MySQL 表就够当队列。
- 指纹、内容哈希、分组键分别解决什么问题。
- Incident 什么时候新建、什么时候升级、什么时候关单。
- 一条 Webhook 从进来到排上诊断任务，数据库里每一步发生了什么。

## 面试怎么讲

**30 秒版本：**
告警入口我们做的是「先落库再处理」。Webhook 只做鉴权和限流，把原文写进 raw_event 表就返回 202，后台单消费者按 id 顺序处理。每条告警算三层身份：对象指纹决定它是谁，内容哈希判断它有没有变化，分组键决定它属于哪个故障。去重和归并在同一个事务里完成；incident 从 candidate 升级为 firing 的那一刻，同一事务里排队诊断任务。这样重复推送不会让数据膨胀，进程崩溃也不会丢事件。

**常见追问：**

- **为什么不用 Kafka 或 Redis 做队列？**
  - 告警量是运维级别：单次最多 100 条，排队上限 1000 条，MySQL 足够。
  - 系统本来只依赖 MySQL，不必多一个中间件。
  - 最关键的是：队列表和 incident、诊断任务在同一个库里，消费一条事件和推进业务状态可以放进一个事务，没有「消息已确认、业务没写成」的双写问题。
- **内存里的唤醒信号丢了怎么办？** 信号只是提醒，真正的队列是表。另外有 1 秒一次的兜底轮询，进程启动时也会主动唤醒一次，处理上次没做完的积压。
- **同一个告警并发到达，会不会建出两个 incident？** 不会。查 last_alert 和查可归并的 incident 都用 `SELECT … FOR UPDATE`，后到的事务要等先到的提交。
- **队列满了怎么办？** 超过 1000 条待处理时拒收，返回 503，Alertmanager 会稍后重试。这比无限堆积、最后把库拖垮要好。
