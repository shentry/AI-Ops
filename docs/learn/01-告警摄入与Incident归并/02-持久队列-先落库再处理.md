# 持久队列：先落库再处理

> 所属：[亮点一 · 告警摄入与 Incident 归并](README.md)

## 一句话

Webhook 把原文写进 `raw_event` 表之后才返回 202；后台只有一个 goroutine，按 id 顺序消费。**表就是队列**，内存 channel 只是「有新活了」的提醒。

## 先弄懂：什么是持久队列

- **队列**：生产者往里放任务，消费者从里面取任务，两边互不等待。
- **持久**：任务存在磁盘（数据库）里，进程死了任务还在。

本项目没有用 Kafka、RabbitMQ 或 Redis Stream，而是用一张 MySQL 表当队列：`status` 字段就是队列状态（pending → processed / failed），按 id 升序取就是先进先出。

为什么够用，为什么这么选：

1. **量不大**：运维告警，单次请求最多 100 条，排队上限 1000 条。
2. **少一个依赖**：系统本来就依赖 MySQL。
3. **能和业务写在同一个事务里（最关键）**：消费一条 raw_event 时，写告警、改 incident、排诊断任务、把 raw_event 标为 processed，全都在一个事务里，要么都成功，要么都回滚、下次重来。如果用外部 MQ，就要处理「消息确认了但业务没写成」或者反过来的双写问题。

## 入口：Webhook handler 做了什么

```go
// 摘自 internal/api/alertmanager.go（有删减）
const (
	maxWebhookBytes    = 1 << 20 // 请求体最大 1MB
	maxWebhookAlerts   = 100     // 单次最多 100 条告警
	maxWebhookInflight = 8       // 同时最多处理 8 个请求
	webhookTimeout     = 10 * time.Second
)

func (h *AlertmanagerWebhook) serveHTTP(w http.ResponseWriter, r *http.Request, rawWriter http.ResponseWriter) {
	// 1. 只接受机器身份（共享 token）。人的登录身份不能往这里推告警
	if actor, ok := h.auth.Authenticate(r); !ok || !actor.Machine {
		w.WriteHeader(http.StatusUnauthorized)
		return
	}
	// 2. 并发闸门：8 个槽位占满就直接 503，让 Alertmanager 稍后重试
	select {
	case h.inflight <- struct{}{}:
		defer func() { <-h.inflight }()
	default:
		w.WriteHeader(http.StatusServiceUnavailable)
		return
	}
	// 3. 超时 + 读截止时间。context 超时打断不了一个很慢的请求体上传，
	//    所以还要给底层连接设置读截止时间
	ctx, cancel := context.WithTimeout(r.Context(), webhookTimeout)
	defer cancel()
	controller := http.NewResponseController(rawWriter)
	deadline, _ := ctx.Deadline()
	controller.SetReadDeadline(deadline)

	// 4. 大小限制（超过 1MB 返回 413）、JSON 解析、条数限制（超过 100 条返回 413）
	payload, err := io.ReadAll(http.MaxBytesReader(w, r.Body, maxWebhookBytes))
	// ……省略错误分支……

	// 5. 落库成功才返回 202
	if _, err := h.db.CreateRawEvent(ctx, ingest.SourceAlertmanager, payload, time.Now().UTC()); err != nil {
		if errors.Is(err, store.ErrInvalidRawEvent) {
			w.WriteHeader(http.StatusBadRequest)         // 不是合法 JSON：调用方的问题
		} else {
			w.WriteHeader(http.StatusServiceUnavailable) // 存储故障或队列已满：我方的问题，请对方重试
		}
		return
	}
	h.worker.Notify()                  // 唤醒消费者
	w.WriteHeader(http.StatusAccepted) // 202：已收下，不代表已处理
}
```

状态码的含义很讲究：**4xx 表示「你的报文有问题，重试也没用」，5xx 表示「我这边暂时不行，请重试」。** Alertmanager 会根据状态码决定是否重发。

## 入队：队列满了就拒收

```go
// 摘自 internal/store/rawevent.go（有删减）
const maxPendingRawEvents = 1000

func (db *DB) CreateRawEvent(ctx context.Context, source string, payload []byte, createdAt time.Time) (RawEvent, error) {
	if len(bytes.TrimSpace(payload)) == 0 || !json.Valid(payload) {
		return RawEvent{}, ErrInvalidRawEvent
	}
	event := RawEvent{Source: source, Payload: payload, Status: "pending", CreatedAt: createdAt}
	err := db.Transaction(func(tx *gorm.DB) error {
		// 锁住所有 pending 行（以及索引上的间隙），再数一数
		var pending []uint64
		tx.Model(&RawEvent{}).Clauses(clause.Locking{Strength: "UPDATE"}).
			Where("status = ?", "pending").Limit(maxPendingRawEvents).Pluck("id", &pending)
		if len(pending) >= maxPendingRawEvents {
			return ErrRawEventQueueFull // 上层返回 503
		}
		return tx.Create(&event).Error
	}, &sql.TxOptions{Isolation: sql.LevelRepeatableRead})
	return event, err
}
```

**为什么要加锁再数？** 如果不加锁，两个并发请求可能同时数到 999，各插一条，队列变成 1001 条。在 REPEATABLE READ 隔离级别下，`FOR UPDATE` 会锁住 pending 这段索引范围（包括间隙），后来的请求必须等前一个提交，数到的就是准确值。

## 出队：单消费者 + 唤醒信号 + 兜底轮询

```go
// 摘自 internal/ingest/worker.go（有删减）

// Notify 由 HTTP handler 调用，绝不能阻塞。
// wake 的容量是 1：连续唤醒多次会合并成一次，但不会丢，
// 因为 drain 每次都会一直处理到队列为空。
func (w *Worker) Notify() {
	select {
	case w.wake <- struct{}{}:
	default:
	}
}

// consume 是唯一的消费 goroutine：单并发保证了 raw_event 的处理顺序。
func (w *Worker) consume(ctx context.Context) {
	ticker := time.NewTicker(time.Second) // 兜底：唤醒信号错过了，1 秒后也会扫到
	for {
		select {
		case <-ctx.Done():
			return
		case <-w.wake:   // 有新事件落库
		case <-ticker.C: // 兜底对账
		}
		w.drain(ctx)
	}
}

// drain 一口气处理到队列为空。出错就返回，当前事件保持 pending，下一轮再试。
func (w *Worker) drain(ctx context.Context) error {
	for {
		event, found, err := w.db.NextPendingRawEvent(ctx) // 取 id 最小的 pending 行
		if err != nil {
			return err
		}
		if !found {
			return nil
		}
		if err := w.process(ctx, event); err != nil {
			return err
		}
	}
}
```

还有两个启动细节：

- `Start` 先探一次队列，数据库或表结构不对就在 HTTP 监听打开**之前**失败，避免出现「对外收了报文却没人消费」。
- 启动成功后主动 `Notify()` 一次，把上次进程没处理完的积压扫掉。

**为什么只用一个消费者？** 为了保证顺序：同一个告警先 firing 后 resolved，必须按这个顺序处理，否则 incident 可能先被关单、又被重新激活。告警的量不需要并发消费。

## 失败二分法：坏报文和坏数据库要分开处理

```go
// 摘自 internal/ingest/worker.go（有删减）
func (w *Worker) process(ctx context.Context, event store.RawEvent) error {
	alerts, err := ParseWebhook(event.Payload)
	if err != nil {
		return w.reject(ctx, event.ID, err) // 报文本身有问题 → 标为 failed，继续处理下一条
	}
	// ……计算身份、校验字段……
	results, err := w.db.ApplyRawEvent(ctx, event.ID, inputs, time.Now().UTC(), hook)
	if err != nil {
		if errors.Is(err, store.ErrInvalidAlertInput) {
			return w.reject(ctx, event.ID, err) // 字段超长等永久错误 → failed
		}
		return err // 数据库问题 → 原样返回，事件保持 pending，下一轮重试
	}
	// 事务已提交，这时打的日志才代表真实发生过的事
	// ……
}
```

| 失败类型 | 例子 | 处理 | 原因 |
|---|---|---|---|
| 报文本身有问题 | version 不是 "4"、status 未知、配置的指纹字段全部缺失、分组键超过 255 字符 | 标为 `failed` 并记录原因，继续处理下一条 | 重试一万次也不会好。如果留在队首，后面的所有告警都会被堵死（队头阻塞） |
| 数据库有问题 | 连接断开、死锁 | 返回错误，事件保持 `pending` | 这是暂时的，下一轮大概率能成功 |

写进 `raw_event.error` 的错误文本会先把换行替换成空格（防止伪造日志行），再截断到 2048 个字符（防止撑爆字段）。因为这段文本来自外部报文，不可信。

## 两个容易忽略的细节

- **`received_at` 取落库时刻，而不是处理时刻。** 积压很多时，如果用 `time.Now()`，所有告警的接收时间都会被压成「刚才」，时间线就乱了。
- **日志要等事务提交之后再打。** 去重、归并的逻辑在事务里执行。如果在事务里打出「incident 已升级」，事务随后又回滚了，这条日志就成了假记录。所以结果先暂存在切片里，提交之后再统一打印。

## 常见追问

- **handler 里调用 `Notify` 时 worker 还没启动，会丢吗？** 不会。channel 容量为 1，信号会留着；即使留不住，worker 启动时会主动扫一次，之后每秒也会兜底扫描。
- **同一条 raw_event 会不会被处理两次？** 不会。`ApplyRawEvent` 一开始用 `SELECT … FOR UPDATE WHERE id = ? AND status = 'pending'` 锁住这一行；等拿到锁时如果状态已经不是 pending，就查不到这一行，整个事务回滚。
