# 为什么告警不能收到就处理

> 所属：[亮点一 · 告警摄入与 Incident 归并](README.md)

## 一句话

告警入口要同时扛住三件事：重复推送、一个故障对应多条告警、处理慢且进程可能崩溃。所以入口只负责「收下并存好」，真正的处理放到后台。

## 先弄懂：Alertmanager 是怎么推告警的

- **Prometheus** 按告警规则（例如「sub2api 的 up 指标为 0 持续 1 分钟」）计算，条件满足就产生告警，交给 Alertmanager。
- **Alertmanager** 负责分组、抑制、路由，然后通过 **webhook** 把一批告警 POST 给接收方。报文格式（v4）如下：

```json
{
  "version": "4",
  "status": "firing",
  "alerts": [
    {
      "status": "firing",
      "labels": {"alertname": "Sub2APIDown", "service": "sub2api", "severity": "critical"},
      "annotations": {"summary": "sub2api is down"},
      "startsAt": "2026-09-26T10:00:00Z",
      "endsAt": "0001-01-01T00:00:00Z",
      "generatorURL": "http://prometheus:9090/graph?g0.expr=up%7Bjob%3D%22sub2api%22%7D%3D%3D0"
    }
  ]
}
```

- `labels` 是告警的身份标签，`annotations` 是给人看的描述，`generatorURL` 指向产生这条告警的 PromQL 表达式。

Alertmanager 有三个行为，决定了入口必须怎么设计：

1. **会重复推。** 告警持续期间，每隔 `repeat_interval` 就重新推一次，内容基本不变。
2. **会推恢复。** 故障消失后，推一条 `status: resolved` 的同名告警。
3. **会重试。** 接收方超时或返回 5xx，Alertmanager 会重发同一批。

## 如果收到就处理，会出什么问题

| 做法 | 后果 |
|---|---|
| 在 HTTP 请求里直接诊断 | 诊断要采证据、调大模型，一次几十秒到几分钟。Webhook 超时 → Alertmanager 重试 → 同一批告警被处理多次 |
| 只放进内存队列 | 进程重启或崩溃时，队列里的告警全部丢失 |
| 每条告警都当成一个故障 | 一次宕机会同时触发 Down、错误率、延迟告警，加上重复推送，会冒出几十个「故障」，各自诊断、各自处置，甚至各自重启一次 |
| 不区分「重复」和「变化」 | 每次重复推送都写一行，表无限膨胀；真正的变化（比如级别从 warning 升到 critical）又可能被当成重复忽略 |

## 本项目的答案：四个动作

1. **接收与处理解耦**：Webhook 只做鉴权、限流和大小检查，把原文存下就返回 202。见[持久队列](02-持久队列-先落库再处理.md)。
2. **持久化**：原文先写进 MySQL 的 `raw_event` 表，崩溃后能接着处理。见[持久队列](02-持久队列-先落库再处理.md)。
3. **两级去重**：分清「是不是同一个告警对象」和「内容有没有变化」。见[告警的三层身份](03-告警的三层身份.md)。
4. **归并成 Incident**：同一服务、同一时间窗内的告警收进一个 Incident，之后的诊断、审批、执行都以 Incident 为单位。见[Incident 归并与生命周期](04-Incident归并与生命周期.md)。

## 三个核心概念

| 概念 | 含义 | 对应的表 |
|---|---|---|
| Raw event（原始报文） | 一次 Webhook 请求的完整原文 | `raw_event` |
| Alert（告警） | Prometheus 规则产生的一个信号 | `alert`（每个版本一行）、`last_alert`（每个告警对象的最新状态） |
| Incident（故障） | 一次故障，可能包含多条告警 | `incident`、`incident_alert`（成员关系） |

## 常见追问

- **为什么返回 202，而不是 200？** 202 Accepted 的语义是「已收下，稍后处理」，准确描述了这里的行为：报文已落库，但还没处理。
- **Alertmanager 自己不是已经分组了吗？** 它的分组只决定「一次推送里带哪几条告警」，不跨推送记忆，也不知道「这些告警在 15 分钟内属于同一次故障」。跨推送的去重和归并只能由接收方来做。
