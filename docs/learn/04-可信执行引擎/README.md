# 亮点四：可信执行引擎

> 返回：[知识库首页](../README.md)

## 一句话（简历写法）

设计生产写操作的可信执行引擎：MySQL 命名锁保证全局只有一个执行器；认领审批时在行锁内复验全部授权条件，并用 CAS 抢占；每个动作按「准备 → 执行前重读现场 → 写一次 → 出错先对账」执行，结果区分已写入 / 未写入 / 未知三态，未知时触发全局急停；进程重启只对账，不重放。

## 它解决什么问题

- **批准之后现场变了**：容器被别人重启过、告警已经恢复、故障范围变了，还要按旧审批执行吗？
- **两个执行者同时执行同一张审批**：进程多开、重启重叠。
- **调用超时了，到底执行了没有**：直接重试可能重启两次；不重试又可能根本没执行。
- **进程在执行途中崩溃**：重启后该怎么办？

## 方案全景

```text
进程启动
  ├─ AcquireExecutorLock：MySQL GET_LOCK，专用连接，拿不到就启动失败
  ├─ 每秒检查一次锁还在不在，丢了就停掉整个进程
  └─ Executor.Start：把上次中断的 executing 审批逐个「对账」（不重放）

Executor.RunOnce（每秒一轮）
  取一张 approved 审批
    └▶ ClaimApprovalExecution（事务：锁 incident → 锁审批单 → 锁服务）
         claimRefusal 重查：过期？hash？规则版本？故障还在？范围变了？
                          急停？服务忙？预算？维护窗口？规则被阻断？
         ├─ 有问题 → 审批单置为 expired（不换目标）
         └─ 通过 → CAS 更新为 executing + operation_id
    └▶ execute
         重验 hash 和版本 → auto 规则须能读到业务流量 → Action.Execute
            ├─ Written=true   → executed
            ├─ Written=false  → aborted（写之前发现现场变了）
            └─ 报错            → Reconcile 读真实状态
                                  ├─ written      → executed
                                  ├─ not_written  → failed（不重试）
                                  └─ unknown      → failed + 需人工核查 + 全局急停
    └▶ persist → FinishExecution（只重试「记录结果」，不重试动作）
         同一事务：状态、事件、验证任务、变更记录、执行历史、待处理问题
```

## 读完本亮点你会知道

- 幂等、至多一次、结果未知这些概念，以及为什么「超时后重试」在运维里很危险。
- 怎么用 MySQL 命名锁实现单实例执行器，为什么锁要绑在专用连接上。
- 认领时重查哪些条件，为什么失败就作废、不换目标。
- 一个动作的完整生命周期：Prepare、Execute、Reconcile，以重启为例，并对比隔离和回退。
- 三种结果分别怎么处理，为什么「未知」要触发全局急停，崩溃后怎么恢复。

## 面试怎么讲

**30 秒版本：**
执行器的目标是「至多写一次，结果可知」。全局只有一个执行器，由 MySQL 命名锁保证，锁绑在一条专用连接上，每秒检查一次，丢了就停进程。认领审批时在行锁里把授权条件全部重查一遍，有任何变化就作废，不换目标。每个动作分三步：Prepare 时冻结现场版本；Execute 前再读一次，现场变了就不写；报错后不直接重试，而是调用 Reconcile 读真实状态，判断是已写入、未写入还是未知。未知就触发全局急停，交给人核对。进程崩溃后只做对账，不重放。

**常见追问：**

- **为什么不用分布式锁，比如 Redis？** 系统只依赖 MySQL，而且执行器只需要一个实例。MySQL 的 `GET_LOCK` 绑定在连接上，连接断了锁自动释放，不会出现「进程死了锁还在」的问题。
- **超时后为什么不直接重试？** 超时只说明「没等到响应」，不说明「没执行」。重启命令可能已经生效，只是响应丢了，直接重试就会重启两次。必须先读真实状态再决定。
- **未知结果为什么要全局急停，而不只停这一个动作？** 超时之后读到「没变」，并不能排除外部系统稍后才把这次写入落地。在人核对之前，任何新动作都可能和这个「迟到的写入」冲突。宁可全停，也不叠加风险。
- **「先读再写」不是有竞态吗？** 有。单靠它确实不够，所以还叠加了单执行者锁、服务锁、revision 比对和 CAS 认领。对于 sub2api 这种写接口不支持版本条件的外部系统，回执里会明确记录「读和写之间的并发修改无法完全排除」。
