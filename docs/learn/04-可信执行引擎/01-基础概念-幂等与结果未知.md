# 基础概念：幂等、至多一次与结果未知

> 所属：[亮点四 · 可信执行引擎](README.md)

## 一句话

对外部系统的写操作，**没有真正的「恰好一次」**：调用可能成功了但响应丢了。所以本项目追求的是「**至多写一次，并且结果可知**」：写之前重读现场，出错之后先读真实状态再下结论，拿不准就停下来交给人。

## 先弄懂：三种投递语义

| 语义 | 含义 | 风险 |
|---|---|---|
| 至多一次（at-most-once） | 最多执行一次，可能一次都没执行 | 漏执行 |
| 至少一次（at-least-once） | 保证执行，可能执行多次 | 重复执行 |
| 恰好一次（exactly-once） | 不多不少，恰好一次 | 跨系统时理论上无法保证 |

消息队列里常用「至少一次 + 幂等」来模拟恰好一次：重复投递没关系，只要重复处理的结果和处理一次一样。

## 先弄懂：什么是幂等

**幂等**：同一个操作执行一次和执行多次，效果相同。

| 操作 | 幂等吗 |
|---|---|
| 把账号设置为「不可调度」 | 是：设两次还是不可调度 |
| 重启容器 | **否**：重启两次就是中断两次 |
| 回退到版本 v12 | 基本是，但回退过程中的中断不是 |

**重启不是幂等的**，这是本项目执行设计的核心难点：不能靠「失败了就再来一次」来保证执行。

**幂等键**：给每次操作一个唯一编号，外部系统看到重复的编号就不再执行。本项目的 `operation_id`（形如 `op-42`）在执行之前就写进数据库，外部系统支持的话，可以当幂等键用。但 Docker 重启、sub2api 的调度开关都不支持幂等键，所以还需要别的手段。

## 先弄懂：超时的歧义

```text
执行器 ──── 重启请求 ────▶ Docker
                           （重启成功）
执行器 ◀──── 响应 ──────── ✗ 网络中断，响应丢了
执行器：超时了……执行了没有？
```

超时只说明「没收到响应」，不说明「没执行」。所以调用结束之后，只有三种可能的认知：

| 结果 | 含义 | 该怎么办 |
|---|---|---|
| **written** 已写入 | 确认写入已生效 | 进入恢复验证 |
| **not_written** 未写入 | 确认没有写入 | 结束，**不重试**，需要新的决策 |
| **unknown** 未知 | 无法确认 | 停下来，交给人核对 |

「报错了」≠「没执行」，「没报错」也 ≠「生效了」。

## 先弄懂：「先查再改」的竞态

一个常见做法是「先读当前状态，确认没变再写」：

```text
执行器：读容器状态 → 启动时间 08:00，和批准时一致
                                          ← 此时有人手动重启了容器
执行器：写入重启命令                        ← 又重启了一次
```

读和写之间有时间窗口，别人可能在这个窗口里改了状态。**单靠「先查再改」不能保证只写一次。**

## 本项目的组合方案

没有一个手段能单独解决问题，所以层层叠加：

| 手段 | 解决什么 | 在哪一篇 |
|---|---|---|
| 单执行者锁 | 本系统内不会有两个执行器同时执行 | [单执行者](02-单执行者-MySQL命名锁与租约.md) |
| CAS 认领 + 服务锁 | 同一张审批只会被认领一次；同一服务同时只有一个处置 | [认领复验](03-认领复验与CAS.md) |
| operation_id 先落库 | 有唯一编号可追溯；外部支持时可当幂等键 | [认领复验](03-认领复验与CAS.md) |
| revision 比对 | 执行前发现现场被别人改过，就不写 | [Action 三步走](04-Action三步走-以重启为例.md) |
| Reconcile 对账 | 报错后读真实状态判断结果，而不是重试 | [结果三态](05-结果三态-急停与崩溃恢复.md) |
| 未知即急停 | 判断不了就停下所有新动作，交给人 | [结果三态](05-结果三态-急停与崩溃恢复.md) |
| 重启只对账不重放 | 崩溃不会导致重复执行 | [结果三态](05-结果三态-急停与崩溃恢复.md) |

剩下的风险（系统外的人恰好在读和写之间动手）无法完全消除，就**如实记录**。比如 sub2api 调度开关的回执里写着：「sub2api 的调度写入不支持版本条件，无法排除读与写之间的并发修改」。

## 常见追问

- **既然不能保证恰好一次，为什么选「至多一次」而不是「至少一次」？** 运维写操作的代价不对称：重启两次、回退两次，可能比没执行更糟。没执行，还有验证失败和通知兜底，人会介入；执行两次造成的损害收不回来。
- **not_written 为什么不自动重试？** 没写成，说明当时的条件不支持，或者现场变了。原来的批准是针对原来的现场的，重试等于在新现场执行旧决策，必须重新走一遍诊断和授权。
