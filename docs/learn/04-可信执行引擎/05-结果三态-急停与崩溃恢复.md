# 结果三态、急停与崩溃恢复

> 所属：[亮点四 · 可信执行引擎](README.md)

## 一句话

每次执行最终落到三种审批状态之一：**executed**（确认写入，进入验证）、**aborted**（写之前放弃，确定没写）、**failed**（写失败或结果未知）。结果未知时触发**全局急停**，所有新动作停下，等人核对后手动恢复。进程重启时，中断的执行只做对账，永不重放。

## 从执行结果到审批状态

```go
// 摘自 internal/approval/executor.go 的 execute（有删减）
receipt, execErr := action.Execute(runCtx, op)
result := executionResult{Action: row.ToolName, OperationID: op.ID, Written: receipt.Written,
	Before: receipt.Before, After: receipt.After, Detail: receipt.Detail}
if execErr == nil {
	if receipt.Written {
		return e.completion(row, "executed", result, receipt.Change) // 写成功
	}
	return e.completion(row, "aborted", result, nil) // 写之前主动放弃
}
// 写操作报错：先读目标的真实状态，再做任何决定。
// 注意这里用新的 context：原来的可能已经超时了
result.Error = execErr.Error()
reconcileCtx, cancel := context.WithTimeout(context.Background(), action.Definition().Timeout)
defer cancel()
return e.reconciled(row, action, op, result, reconcileCtx)
```

```go
// 摘自 internal/approval/executor.go 的 reconciled（有删减）
func (e *Executor) reconciled(row store.Approval, action tools.Action, op tools.Operation, result executionResult, ctx context.Context) store.ExecutionCompletion {
	reconciled, err := action.Reconcile(ctx, op)
	outcome := reconciled.Outcome
	if err != nil {
		outcome = tools.OutcomeUnknown // 连状态都读不到：未知
	}
	switch outcome {
	case tools.OutcomeWritten:
		return e.completion(row, "executed", result, reconciled.Change) // 虽然报错了，但确实生效了
	case tools.OutcomeNotWritten:
		// 确认没写：不重试，需要新的决策
		if result.Error == "" {
			return e.completion(row, "aborted", result, nil)
		}
		return e.completion(row, "failed", result, nil)
	}
	result.ManualCheck = true // 未知：需要人工核查
	return e.completion(row, "failed", result, nil)
}
```

汇总：

| Execute 的结果 | Reconcile 的结果 | 审批状态 | 后续 |
|---|---|---|---|
| Written=true | — | **executed** | 创建恢复验证任务（亮点五） |
| Written=false | — | **aborted** | 打开问题 `execution_aborted`：批准的快照已经和实时对象不符 |
| 报错 | written | **executed** | 同第一行 |
| 报错 | not_written | **failed** | 打开问题 `execution_failed`；不重试 |
| 报错 | unknown | **failed** + 需人工核查 | 打开 `execution_failed` 和 `manual_check`，**触发全局急停** |

## 全局急停

结果未知时，`FinishExecution` 在**同一个事务里**写入一条急停控制事件：

```go
// 摘自 internal/store/execution.go 的 FinishExecution（有删减）
case "failed":
	codes := []string{"execution_failed"}
	if completion.ManualCheck {
		codes = append(codes, "manual_check")
		// 超时后读到「没变」，不能排除外部系统稍后才落地这次写入。
		// 在操作人核对目标并手动恢复之前，停下所有新动作
		tx.Create(&ControlEvent{Kind: ControlEmergencyStop, Actor: "system:execution",
			Reason: fmt.Sprintf("approval %d outcome is unknown; reconcile before resuming", row.ID)})
	}
	for _, code := range codes {
		openIncidentProblem(ctx, tx, IncidentProblem{Code: code, Severity: "error",
			Summary: "execution failed or result uncertain; manual verification required" /* … */})
	}
```

急停生效后：

- Policy 对所有新动作的决策都是「拒绝：emergency stop is active」；
- 执行器认领时同样拒绝；
- 控制台「自动处置」页会显示急停状态和原因；
- 操作人核对完目标的真实状态后，调用 `/api/v1/remediation/resume` 恢复。

急停和恢复都是 `control_event` 表里的记录（谁、什么时候、为什么），判断当前是否急停，就是看最近一条急停 / 恢复事件是哪一种。

## 记录结果：只重试写库，不重试动作

```go
// 摘自 internal/approval/executor.go
// 只有「记录结果」会重试，动作本身永远不会
func (e *Executor) persist(ctx context.Context, completion store.ExecutionCompletion) error {
	for {
		if err := ctx.Err(); err != nil {
			return err
		}
		completion.FinishedAt = time.Now().UTC().Truncate(time.Millisecond)
		err := e.db.FinishExecution(ctx, completion)
		if err == nil {
			return nil
		}
		if errors.Is(err, store.ErrApprovalConflict) || errors.Is(err, store.ErrApprovalNotFound) {
			return fmt.Errorf("execution result commit rejected: %w", err)
		}
		e.logger.Printf("executor: approval %d result commit failed; retrying persistence only: %v", completion.ApprovalID, err)
		time.Sleep(time.Second) // 实际代码用 timer + select，可以被 ctx 取消
	}
}
```

`FinishExecution` 本身是幂等的：审批单已经不是 executing，而且已存的结果和这次的结果一模一样（规范化 JSON 比较），就直接返回成功。所以「写库成功了但响应丢了、又重试一次」不会出问题。

执行完成的同一个事务里还会写入：

| 写入 | 条件 | 用途 |
|---|---|---|
| 审批状态 + 结构化回执（超过 8KB 只存摘要和 SHA-256） | 总是 | 审计 |
| `execution.completed / failed / aborted` 事件 | 总是 | 时间线；failed / aborted 会触发通知 |
| `verify_task`（验证任务） | executed | 亮点五 |
| 变更记录 `change_event` | 回退等部署类动作 | 下次回退要读 |
| 执行历史 `fault_cmd_history` | 主动作且不是 aborted | 同类故障诊断时作为参考注入 |

## 崩溃恢复：只对账，不重放

```go
// 摘自 internal/approval/executor.go 的 Start（有删减）
// 启动时（接收请求之前）调用一次。上一个进程中断的执行，按目标的实际状态对账，永不重放
func (e *Executor) Start(ctx context.Context) error {
	e.db.CheckExecutionLease(ctx)                // 确认拿着锁
	interrupted, _ := e.db.ListExecutingApprovals(ctx) // 所有停在 executing 的审批
	for _, row := range interrupted {
		if err := e.persist(ctx, e.recover(ctx, row)); err != nil {
			return err // 对账失败就不启动：宁可不工作，也不在不确定的状态上继续
		}
	}
	go e.loop(ctx)
	return nil
}

// recover：读目标的实际状态。已生效的进入验证，没生效的结束（不重试），不确定的交给人
func (e *Executor) recover(ctx context.Context, row store.Approval) store.ExecutionCompletion {
	action, op, err := e.operation(row)
	result := executionResult{Detail: "execution interrupted by a process restart" /* … */}
	if err != nil {
		result.Outcome, result.ManualCheck = "unknown", true
		return e.completion(row, "failed", result, nil)
	}
	return e.reconciled(row, action, op, result, ctx) // 和报错后对账是同一套逻辑
}
```

**为什么能判断出「中断」？** 认领时先把状态改成 executing 并提交，然后才调用动作。进程在调用动作期间崩溃，审批单就会停在 executing。重启后看到 executing，说明「开始了但不知道结果」。

**为什么不重放？** 重启不是幂等的。重放可能导致第二次重启，而且「中断前的决定」对应的是中断前的现场。

## 走一遍：三种典型结局

| 场景 | 过程 | 结局 |
|---|---|---|
| 正常 | 认领 → 重读一致 → Docker 重启成功 | executed，进入验证 |
| 有人抢先手动重启 | 认领 → 重读发现启动时间变了 | aborted，不重复重启 |
| Docker 调用超时 | 认领 → 调用超时 → 对账读到启动时间已变 | executed，进入验证 |
| Docker 调用超时且读不到状态 | 认领 → 超时 → 对账也失败 | failed + 需人工核查 + 全局急停 |
| 执行中进程崩溃 | 重启 → 看到 executing → 对账 | 按对账结果落到上面某一种 |

## 常见追问

- **not_written 为什么记 failed 而不是 aborted？** 看有没有报错：写之前主动放弃是 aborted（正常的安全拒绝）；尝试写了但报错、事后确认没生效是 failed（出了故障，需要人关注）。
- **急停会不会太频繁？** 只有「结果未知」才会触发：调用报错，并且对账也无法确认。这种情况本来就需要人介入。
- **对账失败导致执行器启动不了，会不会卡死？** 启动失败会让整个进程退出，运维能立刻发现，比「带着不确定状态继续运行」安全。对账本身只做只读查询，失败通常说明依赖（Docker、sub2api）不可用，这时本来就不该执行任何写操作。
