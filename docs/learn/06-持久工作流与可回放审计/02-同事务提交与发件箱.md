# 同事务提交与发件箱

> 所属：[亮点六 · 持久工作流与可回放审计](README.md)

## 一句话

一个结论和它必然引发的后续，要在**同一个事务**里提交：诊断结论和审批单、执行结果和验证任务、验证裁决和重诊请求。对外的副作用（发通知、打日志）放在提交之后；需要可靠送达的通知，则在写事件的同一事务里写一行通知任务（**发件箱模式**），由专门的 worker 投递。

## 先弄懂：为什么要同事务

假设「诊断结论」和「审批单」分两个事务提交，进程恰好在两者之间崩溃：

```text
事务 1：run 标记为 succeeded，写入 RCA 和 plan   ✓ 已提交
                         ← 进程崩溃
事务 2：写入审批单                                 ✗ 没发生
```

结果：诊断显示成功，却没有审批单。没人知道还有一个动作等着批准，incident 就这样悬着。反过来也一样：审批单写了，诊断却显示失败。

**规则：一个事实和它必然引发的后续，要么都存在，要么都不存在。**

## 项目里的四个关键事务

| 事务 | 一起提交的内容 | 如果拆开 |
|---|---|---|
| `ApplyRawEvent` 摄入 | 告警版本、去重状态、incident 归并 / 升级 / 关单、诊断任务、事件、raw_event 标记为 processed | incident 升级了却没排诊断；或者报文标记已处理，告警却没写进去 |
| `CompleteRun` 诊断完成 | RCA、plan、token 用量、run 终态、审批单草稿、事件（含是否需要人工） | 诊断成功却没有审批单；或者有审批单，诊断却失败 |
| `FinishExecution` 执行完成 | 审批状态和回执、事件、验证任务、变更记录、执行历史、问题、（结果未知时）急停 | 执行成功却没有验证任务，没人验证 |
| `FinalizeVerification` 验证裁决 | 裁决、事件、问题、记忆写入或降级、补偿审批单、重诊任务 | 验证失败了却没重诊；或者重诊排上了，裁决没记下 |

这些事务都由 store 层的一个函数完成，调用方只提交「完成」这一个动作。例如：

```go
// 摘自 internal/diagnose/pipeline.go（有删减）
// 诊断结论和可执行许可一起发布。提交失败时，不发通知，也不做第二次完成，
// 以免有人重新解读一个没提交的结果
if err := p.db.CompleteRun(ctx, store.RunCompletion{
	RunID: run.ID, RCA: rca, PlanJSON: planBytes, TokensIn: tokensIn, TokensOut: tokensOut,
	Status: "succeeded", FinishedAt: finishedAt,
	Approval: draft,  // 审批单草稿（可能为空）
	Events:   events, // run.succeeded，以及（需要人工时）escalation.required
}); err != nil {
	return fmt.Errorf("pipeline: complete run %d: %w", run.ID, err)
}
```

## 外部副作用放在提交之后

有些事情不能放进数据库事务：发飞书消息、打日志。它们必须等提交之后再做：

| 地方 | 做法 |
|---|---|
| 摄入 worker | 事务里的 hook 只把结果存进切片，**提交之后**才打「incident 已升级」之类的日志 |
| 诊断流水线 | 第 6 步「通知」在 `CompleteRun` 之后；通知失败**不改写**已提交的诊断结果 |
| 验证 worker | 只按**已提交**的状态发通知，不按提交前自己算出的结论 |
| 飞书卡片更新 | 审批决策提交后，异步更新卡片（`patchDecisionAsync`） |

```go
// 摘自 internal/diagnose/pipeline.go（有删减）
// 第 6 步在提交之后：通知失败不能改写诊断
notifyErr := p.reporter.NotifyDiagnosis(ctx, report)
notifyType := "notification.sent"
if notifyErr != nil {
	notifyType = "notification.failed"
}
// 记录通知步骤 + 事件；失败时打开问题 notification_failed
```

## 先弄懂：发件箱模式（Outbox Pattern）

「提交之后再发」有个缺陷：提交成功了、发之前进程崩溃，通知就丢了。对「执行失败，需要人处理」这种通知，丢了是不能接受的。

**发件箱模式**的做法：

1. 在写业务数据的**同一个事务**里，往一张「发件箱」表写一行「待发送」；
2. 由一个独立的 worker 扫描发件箱，负责投递和重试；
3. 投递成功后，标记为已发送。

事务提交了，待发送记录就一定存在；事务回滚了，它也一起消失。**不会多发，也不会漏发**（至少一次投递）。

## 本项目的发件箱

所有事件都通过同一个函数追加。它会判断这个事件是否「需要人关注」，需要的话，在同一事务里写一行通知任务：

```go
// 摘自 internal/store/event.go（有删减）
func appendIncidentEvent(ctx context.Context, q *gorm.DB, event IncidentEvent) (IncidentEvent, error) {
	// ……校验……
	if err := q.WithContext(ctx).Create(&event).Error; err != nil {
		return IncidentEvent{}, err
	}
	if requiresHumanAttention(event) {
		// 同一事务：事件在，通知任务就在
		if err := q.WithContext(ctx).Create(&NotificationTask{EventID: event.ID, NextAttemptAt: event.CreatedAt}).Error; err != nil {
			return IncidentEvent{}, err
		}
	}
	return event, nil
}
```

哪些事件需要人关注：

```go
// 摘自 internal/store/notification.go
func requiresHumanAttention(event IncidentEvent) bool {
	switch eventlog.EventType(event.EventType) {
	case "run.failed", "execution.failed", "execution.aborted",
		"verify.failed", "verify.inconclusive", "verify.recurred":
		return true
	case "approval.expired", "notification.failed":
		return true
	case "escalation.required":
		return event.Phase == "diagnosis" // 诊断阶段：结论需要人处理（manual 审批、拒绝、无动作等）
	}
	return false
}
```

注意 `notification.failed` 本身也在列表里：诊断报告那种「提交之后直接发」的通知发送失败了，会通过发件箱再通知一次。

## 投递与重试

```go
// 摘自 internal/notify/worker.go（有删减）
func (w *Worker) RunOnce(ctx context.Context) error {
	task, found, err := w.db.NextNotification(ctx, time.Now().UTC()) // 取一个到期、未投递的任务
	if err != nil || !found {
		return err
	}
	sendCtx, cancel := context.WithTimeout(ctx, 10*time.Second)
	_, sendErr := w.notifier.Send(sendCtx, Notification{Kind: NotificationEscalationRequired,
		Title: "需要人工处理", Summary: fmt.Sprintf("事件 #%d · %s：%s", event.ID, event.EventType, tools.Sanitize(event.Summary)) /* … */})
	cancel()
	failure := ""
	if sendErr != nil {
		failure = tools.Sanitize(sendErr.Error())
	}
	return w.db.FinishNotification(ctx, task, time.Now().UTC(), failure)
}
```

```go
// 摘自 internal/store/notification.go
func (db *DB) FinishNotification(ctx context.Context, task NotificationTask, at time.Time, failure string) error {
	updates := map[string]any{"attempts": gorm.Expr("attempts + 1"), "last_error": nil}
	if failure == "" {
		updates["delivered_at"] = at
	} else {
		updates["last_error"] = truncateStoreText(failure, 512)
		// 退避：5 秒 × 2^min(次数, 6)，即 5s、10s、20s …… 最长 320s
		updates["next_attempt_at"] = at.Add(time.Duration(1<<min(task.Attempts, 6)) * 5 * time.Second)
	}
	// 条件更新：attempts 必须等于读取时的值，防止并发下重复计数
	return db.Model(&NotificationTask{}).
		Where("event_id = ? AND delivered_at IS NULL AND attempts = ?", task.EventID, task.Attempts).
		Updates(updates).Error
}
```

**「重试投递，不重试动作」**：通知任务只包含事件编号和摘要，重试只是再发一次消息，绝不会让触发它的动作再执行一次。

## 常见追问

- **至少一次投递，会不会重复通知？** 会有小概率重复：发送成功了，但标记已发送时失败。对「需要人处理」的通知，重复一条比漏掉一条好得多。
- **为什么诊断报告不走发件箱？** 诊断报告是给人看的常规信息，偶尔丢了影响不大，而且发送失败本身会产生 `notification.failed` 事件，这个事件会走发件箱。所以真正重要的失败不会丢。
- **没有配置通知渠道时怎么办？** 通知 worker 不启动，通知任务会一直堆积在表里。所以配置了 auto 规则、却没有通知渠道时，服务拒绝启动：自动执行出了问题，必须能通知到人。
