# 亮点六：持久工作流与可回放审计

> 返回：[知识库首页](../README.md)

## 一句话（简历写法）

基于 MySQL 构建持久化工作流：告警、诊断、审批、执行、验证、追问、通知七类任务都用「表 + 轮询 + CAS 认领 + 租约恢复」的统一 worker 模型驱动，进程崩溃不丢任务。关键结论和它的后续动作、审计事件在同一事务中提交；需要人关注的事件用发件箱模式可靠投递。每次诊断在调用模型前保存完整输入，可以用冻结快照原样回放，并配套诊断效果评测。

## 它解决什么问题

- 进程崩溃、重启时，正在处理的任务不能丢，也不能重复执行。
- 「状态改了，通知没发」或「通知发了，事务回滚」这类不一致。
- 出了问题，能说清每一步发生了什么、模型当时看到了什么。
- 改了提示词、规则或模型之后，能知道效果变好了还是变差了。

## 方案全景

```text
          ┌──────────────── MySQL（唯一依赖）────────────────┐
          │  队列表：raw_event / agent_run / approval /       │
          │         verify_task / conversation_message /     │
          │         notification_task                        │
          │  审计表：incident_event / agent_run_step /        │
          │         incident_problem / diagnosis_snapshot    │
          └──────────────────────────────────────────────────┘
               ▲ 认领（CAS）      ▲ 同事务提交       ▲ 只追加
               │                 │                  │
  ingest / diagnose / executor / verification / conversation / notify / expiry
  （每个 worker：启动预检 → 回收超时认领 → 循环「取 → 认领 → 处理 → 提交」）

  诊断 ── 调模型前 ──▶ diagnosis_snapshot ──▶ cmd/replay 冻结回放
  归档的真实模型输出 ──▶ tests/effectiveness 评测与回归
```

## 读完本亮点你会知道

- 七个 worker 共用的模型长什么样，怎么保证崩溃不丢、不重复。
- 哪些内容必须同事务提交，发件箱模式怎么保证通知可靠送达。
- 审计三件套（事件、步骤、问题）分别记录什么，控制台怎么用它们。
- 冻结回放怎么做到「不读线上、不执行」，评测怎么设计、结果怎么解读。

## 面试怎么讲

**30 秒版本：**
整个系统只依赖 MySQL，它同时承担业务存储、持久队列和审计。所有异步环节都是同一个模型：任务存在表里，worker 轮询，用条件更新认领，超时的认领被回收重跑。关键结论和它的后续动作放在同一个事务里提交，比如诊断结论和审批单、执行结果和验证任务。需要人关注的事件，在写事件的同一事务里写一行通知任务，由通知 worker 带退避重试投递。每次诊断在调模型前就保存完整输入和证据，事后可以离线冻结回放；我们还用归档的真实模型输出做回归测试。

**常见追问：**

- **轮询会不会浪费资源？** 每秒一次的轻量查询，都走状态索引，对告警级别的负载可以忽略。换来的是没有额外中间件，并且队列和业务状态天然一致。
- **worker 处理到一半崩溃了怎么办？** 认领时记录了时间。超过租约时间还没完成的任务，会被放回队列重新处理。能不能重跑取决于任务的性质：诊断可以重跑；执行不重跑，而是对账（亮点四）。
- **怎么保证通知不丢？** 通知任务和触发它的事件在同一个事务里写入，事件存在，通知任务就一定存在。通知 worker 投递失败会按 5 秒 × 2^n 退避重试，直到成功。
- **回放和重跑有什么区别？** 重跑会读今天的线上状态；回放只用当时记录下的证据和工具结果，没记录的查询返回 missing，并且从不执行动作。所以回放能复现「模型当时为什么这样判断」。
