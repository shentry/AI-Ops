# 冻结回放与效果评测

> 所属：[亮点六 · 持久工作流与可回放审计](README.md)

## 一句话

每次诊断在调用模型**之前**，就把模型将要看到的一切存进回放快照，调用后再补上工具调用和上下文统计。`cmd/replay` 用这份快照离线重跑：工具只返回当时记录的结果，不读线上，不执行动作。另外，项目用 12 个人工构造的证据案例评测诊断效果，并用归档的真实模型输出做回归。

## 先弄懂：为什么需要回放

事后复盘一次诊断时，最想知道的是：**模型当时看到了什么，为什么这样判断？**

如果只是「用今天的数据再诊断一次」，证据已经变了：容器状态变了，指标也变了，得出的结论说明不了当时的问题。必须**冻结**当时的输入，才能：

- **复现**：同样的输入，模型还会这样判断吗？是偶然还是稳定的问题？
- **定位第一个出错点**：是信息没进上下文、工具返回错了、还是模型误读了？
- **回归**：改了提示词或 Guard 之后，用当时的输入再跑一次，看问题是否消失。

## 回放快照里存了什么

`diagnosis_snapshot` 表，每个诊断一行：

| 字段 | 内容 | 写入时机 |
|---|---|---|
| `code_version` | 构建时的 Git 提交号，工作区有未提交改动时带 `-dirty` | 采集证据后 |
| `evidence_json` | 结构化证据（11 项，含结构化事实） | 采集证据后，**调模型之前** |
| `model` | 模型 ID | 调模型之前 |
| `prompt_sha256` | 系统提示词的摘要（提示词版本） | 调模型之前 |
| `tools_json` | 当时可用的只读工具目录 + 可建议的动作定义 | 调模型之前 |
| `input_text` | 模型收到的完整证据文本（含重诊上下文、历史命令） | 调模型之前 |
| `tool_calls_json` | 每次工具调用的参数和**模型实际看到的输出**（出错时就是 `tool error: …`） | 调模型之后（失败也要写） |
| `context_json` | 上下文压缩统计 | 调模型之后 |

**为什么在调模型之前写？** 如果调用过程中进程崩溃，或者模型调用失败，事后仍然能知道这次给模型看了什么。任何一步写不进去，本次诊断就失败，不发布计划：没有可回放记录的诊断，不允许产生动作。

记忆命中的诊断没有模型输入（跳过了模型），快照里只有证据。

## 回放怎么做到「不碰线上」

```go
// 摘自 cmd/replay/main.go（有删减）
// 用冻结的快照重跑一次诊断。模型收到记录下的输入，只能计划记录下的动作；
// 工具只返回记录过的结果，没记录的查询返回明确的 "missing"，而不是去读今天的线上状态。
// 从不 Prepare、不执行动作，也不写任何东西
//
//	go run ./cmd/replay -config config.yaml -run 123

registry, calls, err := frozenRegistry(snapshot)   // 用记录下的工具输出构造一个「冻结」的注册表
reasoner := llm.NewReasoner(llm.NewFactory(cfg.LLM), registry, cfg.Diagnose.Budget)
result, diagnoseErr := reasoner.Diagnose(ctx, *snapshot.InputText, run.Mode, /* … */)

report := map[string]any{
	"run_id": runID, "recorded_code_version": snapshot.CodeVersion,
	"recorded_model": snapshot.Model, "replay_model": input.Model,
	// 提示词摘要不同，说明代码或动作目录变了：这时回放是回归检查，而不是复现
	"prompt_matches":   *snapshot.PromptSHA256 == input.PromptSHA256,
	"original":         map[string]any{"rca": run.RCAText, "plan": run.PlanJSON},
	"tool_calls":       calls.total,
	"unrecorded_calls": calls.missing, // 模型这次查了当时没查的东西
}
if result != nil {
	guard := diagnose.Guard(result.RCA, result.Plan, evidence) // 用当时的证据跑当前的 Guard
	report["replay"] = map[string]any{"rca": result.RCA, "plan": result.Plan, "guard": /* … */}
}
```

冻结注册表的行为：

- 模型调用的工具和参数与当时一样 → 按顺序返回当时记录的输出；
- 模型这次查了当时没查过的东西 → 返回 `{"missing": "this query was not recorded in the frozen snapshot; live state is not read during replay"}`；
- 记录下的动作只能被「计划」，永远不能写入。

输出是一份 JSON 报告：原始结论和回放结论并排，加上提示词是否一致、有几次未记录的查询、当前 Guard 对回放结论的判断。

## 效果评测：`tests/effectiveness`

### 设计

- **12 个人工构造的证据快照案例**：进程退出、身份不明的 OOM、配置缺失、数据库认证失败、Redis 不可达、数据库连接槽耗尽、上游限流、磁盘写满、证据不足、已恢复的事件、无关的 OOM 噪声、日志提示词注入。
- 每个案例写明：期望的诊断（**只给评审看，不发给模型**）、必须引用的证据、允许的动作、允许的置信度、允许的目标、Guard 对重启的期望。
- 走的是真实代码路径：`Evidence.Render → Reasoner.Diagnose → Guard`，调用真实模型。
- 每次保存：原始 RCA、置信度、证据引用、建议动作、**模型原始计划和 Guard 结论分开记录**（避免 Guard 的拦截掩盖模型本身的问题）、工具轨迹、token 用量、耗时。

### 自动检查只判断三件事

1. 引用的证据段落存不存在，有没有包含必需的证据；
2. 建议的动作和目标在不在允许范围内；
3. 证据不足的案例，置信度有没有降下来。

**自动检查通过 ≠ 根因正确。** 所有输出初始都标记为「等待人工评审」，评审要逐条记录完整正确、部分正确、错误、合理弃答，并附具体依据。

### 2026-09-22 的结果（DeepSeek V4 Flash，12 个案例 × 3 次）

| 指标 | 结果 |
|---|---|
| 完成诊断（无模型错误） | 36 / 36 |
| 自动检查通过 | 34 / 36 |
| 中位耗时 / P95 | 约 6.3 秒 / 约 9.9 秒 |
| 只读工具调用 | 51 次 |
| 实际修复次数 | 0（评测不执行动作） |

### 先弄懂：Pass@k 和 Pass^k

同一个案例跑 k 次：

- **Pass@k**：k 次里**至少一次**成功。衡量「能力上限」，适合可以挑选结果的场景。
- **Pass^k**：k 次**全部**成功。衡量「稳定性」，适合要求每次都对的业务场景。

如果单次成功率是 p，且各次独立，那么 Pass@k = 1 − (1 − p)^k，Pass^k = p^k。例如 p = 0.6、k = 5 时，Pass@5 ≈ 99%，Pass^5 ≈ 8%。**两者不能互相代替。**

用归档结果按案例计算（自动检查口径）：

| | 结果 |
|---|---|
| Pass@3 | 12 / 12 |
| Pass^3 | **11 / 12** |
| 不稳定的案例 | `oom_unidentified`（3 次里 2 次错误地建议重启） |

自动化运维要求的是「每次都对」，所以看 Pass^3。这个不稳定的案例就是[亮点三的案例](../03-确定性闸门与规则授权/06-案例-一次漏放的定位与修复.md)，修复在 Guard 里，回归测试 `TestRecordedPlansPolicyReplay` 直接用这 3 次归档输出。

### 评测的边界

- 这是**人工构造**的证据快照，不是历史生产故障集，也不是故障注入；
- 测的是诊断到 Guard 为止，**没有测执行后能否真的修好**；
- 测的是诊断总耗时，不是首次正确定位时间，更不是 MTTR（平均修复时间）。

## 线上效果报表

控制台「自动处置」页有一份从真实处置记录计算的效果报表：

| 指标 | 定义 |
|---|---|
| 错误执行率 | 复盘判为错误的执行 / 已复盘的执行 |
| 无人介入恢复率 | 自动动作恢复（验证稳定 + 原告警已恢复）且没有记录到人工干预的 incident 占比 |
| 恢复耗时 | 从 incident 开始到验证通过（中位数、最大值） |
| 复发率 | 进入观察期后复发的比例 |
| 人工占比 | 需要人工处理的 incident 占比和耗时 |
| 成本 | token 用量、每个 incident 的平均 token |
| 根因准确率 | 只基于人工复盘过的诊断；「未知」单独计数，不算正确 |

每个比率都附原始计数；分母为 0 时显示为空，而不是 0%，**小样本不会显示成「零风险」**。报表注释还特别说明：「没有记录到人工干预」不等于「确认没有人工干预」，人可能在平台之外操作过。

## 常见追问

- **回放时模型输出和原来不一样，说明什么？** 模型本身有随机性，所以要看多次回放的结果分布。如果提示词摘要也变了，说明代码或动作目录已经改过，这次回放是回归检查而不是复现。
- **为什么要把模型原始计划和 Guard 结论分开记录？** 如果只记最终结果，Guard 拦下的错误会让模型看起来「没问题」。分开记录，才能分别评估「模型有多可靠」和「系统有多安全」。
- **评测为什么不直接给一个「准确率」？** 自动检查只能判断格式和范围，判断不了根因对不对。把自动检查通过率说成准确率，是在误导。根因准确率只来自人工评审。
