# 审计三件套：事件、步骤、问题

> 所属：[亮点六 · 持久工作流与可回放审计](README.md)

## 一句话

三张审计表各答一个问题：**事件**（`incident_event`）回答「按时间顺序发生了什么」，**步骤**（`agent_run_step`）回答「一次诊断里每一步的输入输出是什么」，**问题**（`incident_problem`）回答「现在有哪些事需要人处理」。事件和步骤只追加、不修改；问题可以打开、关闭，是派生出来的读模型。

## 先弄懂：只增不改（Append-only）

**只增不改**：原始记录只追加，从不修改或删除。要纠正，就追加一条新记录。

好处：

- **可追溯**：任何时刻的状态都能从历史里还原；
- **可重放**：事件流可以原样重新读一遍；
- **防抵赖**：没有「悄悄改掉」的可能。

需要注意的是：只增不改针对的是**原始事实**。从事实派生出来的视图（比如「当前有哪些待处理问题」「故障记忆」）是可以更新的，不能永远沿用旧结论。

## 一、事件：`incident_event`

每个 incident 的完整时间线。事件类型一共 40 多种，覆盖全流程：

| 阶段 | 事件类型 |
|---|---|
| incident | `incident.created`、`incident.promoted`、`incident.resolved` |
| 诊断 | `run.queued`、`run.started`、`run.succeeded`、`run.failed`、`run.stalled` |
| 取证 | `collector.started`、`collector.completed`、`collector.failed` |
| 模型 | `llm.started`、`llm.tool_called`、`llm.completed`、`llm.failed` |
| 闸门 | `guard.evaluated`、`guard.overridden`、`policy.evaluated`、`policy.degraded` |
| 审批 | `approval.created`、`approval.approved`、`approval.denied`、`approval.expired` |
| 执行 | `execution.started`、`execution.completed`、`execution.failed`、`execution.aborted`、`compensation.queued` |
| 验证 | `verify.queued`、`verify.started`、`verify.checked`、`verify.passed`、`verify.failed`、`verify.inconclusive`、`verify.stable`、`verify.recurred` |
| 其他 | `retry.scheduled`、`escalation.required`、`review.recorded`、`notification.sent`、`notification.failed`、`conversation.asked`、`conversation.answered`、`conversation.failed` |

每条事件的字段：incident、可选的 run 和审批单、类型、阶段、状态、摘要（脱敏，最多 512 字符）、可选的 JSON 载荷、时间。

事件有三个用途：

1. **时间线**：控制台的事件时间线组件直接渲染它；
2. **实时流**：控制台通过 SSE 按事件 ID 增量推送（亮点七）；
3. **业务判断的依据**：规则阻断就是查「这条规则最近一次重置之后，有没有 `verify.failed` 等事件」（亮点五）；人工重诊的 1 分钟冷却，是查最近一条 `run.queued` 事件。

**事件是事实，也是状态的依据**，所以它必须和业务状态在同一个事务里写入（上一篇）。

## 二、步骤：`agent_run_step`

一次诊断（一个 agent_run）内部的逐步记录，用 seq 编号排序：

| seq | 步骤 | 输入 | 输出 |
|---|---|---|---|
| 1 | 记忆查找 | 故障指纹、是否重诊 | 是否命中、命中次数 |
| 2 | 证据采集 | run 和 seq | 渲染后证据的摘要 |
| 3 | 模型推理 | — | 压缩次数、估算和实际 token、工具调用次数、置信度、RCA |
| 30–89 | 工具调用（每次一条，最多 60 条） | 工具参数 | 工具输出（模型实际看到的内容） |
| 4 | Guard | 动作和目标 | `decision=… overridden=… reason=…` |
| 5 | Policy | 动作和规则 | 决策和原因 |
| 6 | 通知 | 诊断报告 | Guard 结论 |
| 90 | 恢复验证结论 | — | 观测、详情、连续次数 |
| 91 | 观察期结论 | — | 同上 |
| 92 | 补偿的验证结论 | — | 同上 |

- 工具调用从 30 开始编号，排序后自然落在「推理」之后；上限 60 条，和 30～89 的号段对齐，不会撞上 90。超过 60 条时记一条「已截断」。
- 每条步骤的输入输出都经过脱敏，并截断到 1024 个字符：审计要能回放，但不把整份证据大文本塞进步骤表（完整内容在回放快照里）。
- **失败的诊断也要留下步骤**。Reasoner 失败时会返回「审计残骸」：失败前调了哪些工具、烧了多少 token。

步骤还会被下游读取：写入故障记忆时，要检查第 4 步 Guard 的输出是否以 `decision=allow overridden=false` 开头（亮点五）；重诊时，要读上一轮第 90 步的验证失败详情，注入证据（亮点二）。

## 三、问题：`incident_problem`

「待处理问题面板」：每个 incident 当前有哪些需要人关注的问题。

```go
// 摘自 internal/store/problem.go 的注释
// incident_problem 问题面板。open/resolve 都是幂等的 upsert 语义，
// 同一个 code 重复上报只会续 last_seen_at。
// 问题只能 open 或 resolve，禁止通过批次接口传入任意操作。
```

问题以「incident + 问题码」为唯一键。常见的问题码：

| 问题码 | 严重度 | 何时打开 | 何时关闭 |
|---|---|---|---|
| `collector_failed_<证据名>` | warning | 这项证据采集失败 | 下次采集成功 |
| `reasoner_parse_failed` / `reasoner_timeout` | warning | 模型输出不合契约 / 超时 | — |
| `tool_repeated` | warning | 同一工具同参数第 3 次调用 | — |
| `guard_overridden` | warning | Guard 改写了建议 | — |
| `policy_blocked` / `policy_degraded` | warning | Policy 拒绝 / 降级 | — |
| `notification_failed` | warning | 诊断通知发送失败 | 下次发送成功 |
| `approval_near_expiry` | warning | 审批快过期 | 审批过期时 |
| `execution_aborted` | warning | 执行前发现现场变了 | — |
| `execution_failed` | error | 执行失败 | 后续执行成功 |
| `manual_check` | error / critical | 结果未知，或自动重诊次数用完 | 人工处理 |
| `verify_failed` / `verify_inconclusive` | warning | 验证失败 / 无法判断 | 验证通过 |
| `recurred` | critical | 恢复后复发 | 人工处理 |

**问题和事件的区别**：事件是「发生过什么」，永远不变；问题是「现在还有什么没解决」，会随着新事实打开或关闭。同一个问题反复出现，不会生成很多条记录，只会更新最近出现时间。

问题和事件、步骤一样，通过同一个批次接口在同一个事务里写入：一条步骤和它引发的事件、问题变更一起提交。

## 控制台怎么用这三张表

| 组件 | 读哪张表 |
|---|---|
| 事件时间线（EventTimeline） | `incident_event`，通过 SSE 实时追加 |
| 处理流程（FlowStrip） | 按事件和步骤的阶段，渲染出「告警接入 → 证据采集 → 模型诊断 → Guard 校验 → Policy 判定 → 人工审批 → 执行动作 → 恢复验证」8 个阶段的进度 |
| 诊断轨迹（AgentTrace） | `agent_run_step`：每一步的输入输出（点流程节点直接展开对应步骤） |
| 当前问题（ProblemsCard） | `incident_problem`：当前未关闭的问题 |

## 常见追问

- **三张表的数据会不会重复？** 有意冗余：同一件事在事件里是「时间线上的一个点」，在步骤里是「这次诊断的第几步和它的输入输出」，在问题里是「一个待处理项」。它们服务不同的读取场景。
- **步骤为什么要截断？完整内容呢？** 步骤表是给人快速浏览的；完整的模型输入和工具输出在 `diagnosis_snapshot` 里，给回放用（下一篇）。
